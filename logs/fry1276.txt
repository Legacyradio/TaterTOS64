[2026-06-02] *** ROOT CAUSE FOUND + FIX *** (the B2 bug)
======================================================================
EVIDENCE (delivery-window instrumentation): QEMU 11 DOES deliver the DHCP
offers — E1000_RX_GOT fired 3x: "tail=N len=590 status=0x07 eop=2 err=0xaf cb=1".
RDH advanced 0->1->2->3. The frames are valid (590B, DD+EOP). BUT our consume
check `if (eop && !err && len>0 && g_rx_cb)` DROPS them because the descriptor
errors byte reads 0xaf (!err == false).
ROOT CAUSE (TaterTOS bug, latent for ~years): e1000_init set g_rx_ring[i].status=0
but NEVER initialized g_rx_ring[i].errors (or length/checksum/special). The DMA
ring page from pmm_alloc_page_below is NOT zeroed -> errors = garbage (0xaf).
QEMU v11.0.1 e1000 RX (verified in hw/net/e1000.c source) reads the descriptor,
sets only status/length/special, and writes it back WITHOUT touching errors ->
our garbage errors survives -> rx_poll rejects every received frame. The old
Windows QEMU happened to leave errors=0, masking the bug; QEMU 11 preserves it.
FIX [KEEP]: e1000.c e1000_init RX setup loop now zeroes the WHOLE descriptor
(addr/length/checksum/status/errors/special) per entry. (Recycle path already
zeroes status/errors/length, so only first-use was affected — but that first
use is the DHCP offer.)
Rebuilding to verify DHCP + the claude probe now reach the network.
