---------------------------------------------------------------------
ROOT CAUSE (proved via a sched_futex_miss diagnostic)
---------------------------------------------------------------------
Diagnostic showed: the FUTEX_WAIT caller was current[cpu] AND already
PROC_WAITING (state=2). sched_block_futex searches for RUNNING (or rq
membership), finds neither -> -ESRCH. Two bugs let a WAITING task keep
running / re-enter:
  A) sched_yield() == sched_tick(), and sched_tick RETURNED without
     switching when the runqueue was empty (top `if (!q->head) return`) or
     when next==cur. So a task that set itself PROC_WAITING and yielded,
     but whose CPU had nothing else queued at that instant, kept running.
     Its next futex wait then saw a non-RUNNING "current" -> -ESRCH.
  B) SMP race: a thread on the other CPU waking the caller (-> RUNNING) at
     the same moment the caller re-enters sched_block_futex flips the
     caller's state to WAITING transiently.

---------------------------------------------------------------------
FIX (src/kernel/proc/sched.c)
---------------------------------------------------------------------
1. Per-CPU idle fallback: track idle_task[MAX_CPUS] (set in sched_init).
   In sched_tick, when the current task is NOT PROC_RUNNING (it blocked
   itself) and there is no other runnable task, switch to this CPU's idle
   task instead of returning. Applied in BOTH the empty-runqueue branch and
   the next==cur/next==NULL branch. A blocked task can now never keep
   running. Benefits all blocking paths (futex, poll, ...), not just futex.
2. sched_block_futex accepts the caller whether RUNNING or transiently
   WAITING (it is always the current/running task) and re-blocks on the new
   key — a stale wait is superseded. No more -ESRCH for a real wait.
