STEP 2 — Diagnosed the "--list /" failure (NOT cosmetic)
---------------------------------------------------------------------
Contradiction: 25 files copied to root in the same run (proves root reads
as a DIR at copy time) yet "--list /" reads root as type=0 (not a dir).

Root cause: tools/totcopy.c read_inode()/write_inode() located the inode
table via the COMPILE-TIME CONSTANT TOTFS_INODE_TABLE_BLK, while mktotfs
places the inode table at the SHIFTED superblock value
sb.inode_table_start = TOTFS_BLOCK_BITMAP_BLK + bitmap_blocks. With a
single-block bitmap (<=128 MB) bitmap_blocks==1 and the two coincided
(shift 0). For the 400 MB NVMe, bitmap_blocks==4, so the inode table
moved +3 blocks and the two diverged:
  - mktotfs wrote the real root inode (type=DIR) at sb.inode_table_start.
  - totcopy read/wrote inodes at the old constant block (now inside the
    zeroed bitmap region) -> built a phantom root (type stayed 0) and
    appended all 25 dirents there.
  - Copies "succeeded" only because resolve_path("/") short-circuits and
    returns ROOT_INODE WITHOUT the type check (the type!=DIR guard runs
    only inside the path-component loop, which "/" skips). do_list()
    DOES check type -> "not a directory".

Boot impact (the real danger): the kernel (src/kernel/fs/totfs.c
totfs_read_inode, lines 103/119/126) correctly uses
fs->sb.inode_table_start. So at boot the kernel would read mktotfs's
PRISTINE EMPTY root (only "." / "..") and never see the 25 files totcopy
wrote at the wrong location -> /RCLAUDE.LXE unreachable. The build would
have looked fine and the boot would have silently failed to find claude.

---------------------------------------------------------------------
STEP 3 — Fix (patch-based, tools/totcopy.c only; kernel already correct)
---------------------------------------------------------------------
WHY: align totcopy's inode addressing with the on-disk authority (the
superblock), which is what both mktotfs writes and the kernel reads.
Changed 3 sites from TOTFS_INODE_TABLE_BLK to g_sb.inode_table_start:
  - read_inode():  read_block(g_sb.inode_table_start + blk_idx, ...)
  - write_inode(): read_block / write_block(g_sb.inode_table_start + ...)
g_sb is the file-scope superblock (line 24), loaded at image-open before
any inode access, so it is valid at these call sites. Allocator + both
bitmaps already used superblock fields; only inode addressing was stale.
No kernel change (kernel was already superblock-correct, per handoff).

ROOT CAUSE #2 (GPT partition type GUID mismatch — boot-blocking):
The kernel gates ToTFS secondary-mount on guid_eq(p.type_guid,
TOTFS_PART_GUID) (vfs.c:1684). build_iso.sh created the NVMe GPT with
  sgdisk --typecode=1:46544F54-0053-5441-4552-544F53363400
which serializes (GPT mixed-endian) to on-disk bytes
  54 4F 54 46 53 00 41 54 45 52 54 4F 53 36 34 00
but the kernel's TOTFS_PART_GUID (totfs.h) is
  46 54 4F 54 00 53 54 41 45 52 54 4F 53 36 34 00
First 8 bytes differ -> guid_eq() false -> ToTFS partition not recognized
-> /nvme never mounted -> vfs_open("/nvme/RCLAUDE.LXE")==NULL -> skip.
Verified empirically: xxd of NVMe LBA2 == 54 4F 54 46 ... ; superblock
magic at LBA2048 == 46 54 4F 54 (=0x544F5446 TOTFS_MAGIC, correct), so
totfs_probe WOULD pass — only the GUID gate blocked it. (part_init() is
skipped in live mode, but vfs_mount_secondary reads the GPT itself, so
that is not the cause.)

STEP 9 — ROOT CAUSE of the hang (NVMe poll yields from idle ctx)
---------------------------------------------------------------------
Two instrumentation passes (wait_cq_irq beacons, then full read-path:
nvme_io_rw_for_ctrl/poll_cq) gave the definitive trace. MSI is OFF
(irqc=0) so io_q reads use poll_cq. Trace:
  lba 2069-2071: PCQ enter cur=0x0     pid=0 -> done ok=1  (works)
  lba 2096:      PCQ enter cur=0xffffffff81e1b0c0 pid=0 -> done ok=1
  lba 2097:      PCQ enter cur=0xffffffff81e1b0c0 pid=0
                 PCQ: first yield spin=0 -> HANG (silence)
proc_current() returns the per-CPU IDLE task (kernel addr, pid 0) once the
scheduler is fully up and the probe processes have exited (current[cpu] =
idle, sched.c:349). poll_cq's yield guard was just `proc_current()` (non-
null), so from the idle/boot context it called sched_yield() -> scheduler
switched into idle_loop and NEVER returned to kernel_main's read -> the
in-flight read (and all of kernel_main after it) is abandoned -> total
hang. Earlier reads worked only because current[cpu] was still NULL
(busy-poll, no yield). pid 0 is reserved/invalid (process.c:765,789).

---------------------------------------------------------------------
STEP 10 — FIX: never yield/sleep from the pid-0 idle/boot context
---------------------------------------------------------------------
WHY: yielding the CPU is only safe from a REAL schedulable process (pid
!= 0) that the scheduler will resume. The idle/boot context (NULL or pid
0) must busy-poll for the NVMe completion (exactly what worked before the
scheduler came up). Patched src/drivers/storage/nvme.c:
  - poll_cq: yield only if (yc = proc_current()) && yc->pid != 0.
  - wait_cq_irq: take the pause/busy path if (!cur || cur->pid == 0 ||
    !cpu_irqs_enabled()).
This is a genuine driver concurrency bug exposed by reading claude off
NVMe during the live LINUXTEST phase, NOT a beacon artifact.
