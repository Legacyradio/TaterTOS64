The old crash is absent:

Last syscall line before timeout:
  TBTRACE enter pid=12 tgid=12 nr=9 mmap a1=0 a2=2000000000 a3=3 a4=4022 a5=ffffffff a6=0

There is no matching return for that mmap.

Decoded request:
  - length = 0x2000000000 = 128 GiB
  - prot   = 0x3 = PROT_READ | PROT_WRITE
  - flags  = 0x4022 = MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE
  - fd     = -1
  - offset = 0

Claude/JSC successfully completed earlier smaller anonymous mappings with
flags 0x4022, including 0x240000, 0x40000000, 0x40010000, and 0x10000.
The hang is size-specific: the current Tater Bridge mmap path eagerly
allocates/maps every page, so a 128 GiB MAP_NORESERVE reservation turns
into a massive page-allocation loop instead of a sparse virtual-address
reservation.

Other observed syscall tail items returned and are not the hang:
  - nr=96 returned -ENOSYS repeatedly (gettimeofday on Linux x86_64)
  - nr=99 returned -ENOSYS (sysinfo)
  - nr=157 returned -ENOSYS (prctl)
  - nr=436 returned -ENOSYS (close_range)
  - ioctl(TIOCGWINSZ-style requests) returned -ENOTTY

One existing FUTEX_WAKE_BITSET probe reported a failure during this traced
boot. Treat that as a trace/timing perturbation until reproduced without
serial tracing; it is not the Claude pid-12 blocker because the final pid
12 line is the huge mmap entry.

---------------------------------------------------------------------
CONCLUSION / NEXT
---------------------------------------------------------------------
The immediate next blocker is Tater Bridge mmap reservation semantics for
large anonymous private MAP_NORESERVE mappings. JSC is reserving a 128 GiB
address-space cage. Linux reserves virtual address space sparsely here;
Tater Bridge currently tries to back it eagerly.

Next fix:
  - teach LNX_mmap to recognize anonymous private MAP_NORESERVE reservations
    and record a sparse VM reservation instead of allocating every page
  - keep this native to TaterTOS64v3 VM metadata; do not import Linux kernel
    behavior or code
  - rebuild clean with STAGE_CLAUDE=1
  - boot once with the same pid-12 trace and confirm the 128 GiB mmap returns
    instead of hanging
  - then harvest the next real Claude blocker
