fry1314 - sparse MAP_NORESERVE reservation for Claude/JSC cage mmap
=====================================================================
DATE: 2026-06-03 19:48:03 CDT
GOAL: Fix the fry1313 blocker where real Claude entered a 128 GiB
anonymous private MAP_NORESERVE mmap and never returned because Tater
Bridge eagerly allocated every page.

TERMINOLOGY:
  The Linux-compatible ABI layer is Tater Bridge. This fix is native
  TaterTOS64v3 VM/syscall behavior. No Linux kernel code was imported.

---------------------------------------------------------------------
FIX
---------------------------------------------------------------------
Patched src/kernel/proc/linux_compat.h:
  - renamed the file comment to Tater Bridge terminology
  - added LNX_MAP_NORESERVE = 0x4000

Patched src/kernel/proc/syscall.c:
  - added a Linux-prot-to-FRY-prot helper for VM metadata paths
  - added sparse reservation support for large Linux mmap requests that are:
      MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE
      non-MAP_FIXED
      >= 4 GiB
  - sparse reservations are recorded as native fry_vm_region entries:
      FRY_MAP_PRIVATE | FRY_MAP_ANON | FRY_MAP_RESERVE
      FRY_VM_REGION_ANON_PRIVATE
      committed = 0
  - no user pages are allocated for the sparse reservation
  - MAP_FIXED now first tries vm_unmap_region_range() so fixed submaps
    carve holes out of an existing sparse reservation before eager mapping
  - munmap first tries vm_unmap_region_range() so sparse reservation ranges
    can be removed without walking millions of unmapped pages
  - mprotect first tries vm_mprotect_region_range() so committed subranges
    of a sparse reservation can be handled by the native VM path

WHY:
  Linux treats the JSC 128 GiB MAP_NORESERVE request as virtual address
  reservation. Tater Bridge was treating it as immediate physical backing.
  That is wrong for large runtime cages and caused the QEMU timeout at the
  syscall entry line.
