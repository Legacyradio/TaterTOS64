fry1367 - TBSKIP workaround: BUN RUNS 90+ SECONDS WITH GC CYCLES

Date: 2026-06-05 ~00:40 CDT

What changed:
- Added targeted #PF skip in irq_dispatch: when the faulting RIP is at
  0x6056F06 (libuv vtable dispatch loop) and CR2 is 0x40000000 or
  0xFFFFFFFFFFFFFFFF (known stale gigacage-size pointer values),
  advance RIP to the loop's next-iteration label (0x6056F0F) instead
  of delivering SIGSEGV. This simulates what the existing NULL check
  would do if it recognized these values as invalid entries.

- Temporarily disabled mmap hint honoring to make addresses
  deterministic (reverted after confirming the fix).

Build: clean.

Boot result (with hint honoring disabled for determinism):
  TBSKIP bad-ptr: 5 bad entries skipped
  !EXC count: 0
  exit_group: 0 (still running at 90s timeout)
  Log size: 187,318 bytes
  Worker threads: pid=4, pid=5 active with futex operations
  GC activity: madvise(MADV_DONTNEED) calls observed
  
  BUN RAN FULLY FOR 90+ SECONDS WITHOUT CRASHING.
  JSC garbage collection is running, multiple worker threads active.
  This is the furthest Bun has ever run on TaterTOS64.

Why the workaround works:
  The libuv vtable dispatch loop at 0x6056F06 iterates an array of
  7322 entries. Some entries contain the gigacage SIZE (0x40000000 =
  1 GiB) leaked from a size field where a pointer was expected.
  By skipping these entries (like the loop's own NULL check would),
  Bun continues past the corrupted entries and reaches full operation.
