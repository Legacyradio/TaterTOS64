fry1371 - closed statm/scheduler/sigsuspend ABI holes, liveness remains

Date: 2026-06-05 ~08:43 CDT

What changed:
- Added Linux syscall 144 (`sched_setscheduler`) for Tater Bridge.
  Host Linux `claude --version` calls this after worker `clone3`.
  Tater Bridge previously returned `-ENOSYS`; now it accepts
  `SCHED_OTHER` with optional `SCHED_RESET_ON_FORK` and validates pid
  and the scheduler parameter pointer.
- Added `/proc/self/statm` in tbridgefs.
  Host Linux reads it before the successful `claude --version` output.
  Tater Bridge previously returned ENOENT; now the file opens and emits
  Linux page-count fields.
- Added Linux syscall 130 (`rt_sigsuspend`).
  After statm/scheduler were closed, Tater Bridge hit repeated
  `nr=130 unknown -ENOSYS` in a Claude worker. The syscall now validates
  sigset size, installs the temporary mask, blocks/yields, restores the
  old mask, and returns `-EINTR`.
- Made Claude syscall tracing follow the actual Claude tgid dynamically.
  This keeps traces useful when `-smp 8` changes the first Claude pid
  from 3 to 9.
- Restored the final launcher to prompt mode:
    claude -p "say hello from TaterTOS in 10 words"

Conclusion:
- The closed surfaces are real ABI holes, not speculative cleanup:
  statm, sched_setscheduler, and rt_sigsuspend all appear on the
  successful Linux path or the current Tater Bridge path.
- Claude/Bun is still mechanically stable but does not reach CLI output.
  The blocker is now narrowed past missing statm/sched_setscheduler/
  rt_sigsuspend into JSC GC/futex/signal coordination semantics.
- The adjacent JSC parking-lot futex addresses (`...e8c8` waits and
  `...e880` wakes) are normal Linux behavior by themselves; host Linux
  also does that before progressing.
