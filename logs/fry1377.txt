  It is an open-addressing linear-probe hash lookup, 16-byte entries, empty
  sentinel = -1. Exits ONLY on target-found or empty-slot-found. It exits on
  neither -> the table has NO -1 empty slot and does not contain the target.
  A correct hash table always keeps >=1 empty slot so probes terminate.

ROOT-CAUSE CHAIN (high confidence)
  - Empty sentinel value is 0xffffffffffffffff (-1) == the value seen in the
    earlier "corruption" (TBSKIP slotval=0xffffffffffffffff).
  - The other corrupt value, 0x40000000, == the gigacage mmap length exactly
    (mmap len=0x40000000). A SIZE value is leaking into slots that should hold
    -1 empty sentinels (or pointers). With empties overwritten by 0x40000000,
    the probe never sees -1 -> infinite loop -> main thread (pid=3) wedges
    holding JSC heap lock 0x63ad6e0 -> all workers starve (10s condvar retry).
  - This unifies fry1374-1376: the "butterfly corruption" and the "deadlock"
    are the SAME bug: garbage (0xff / 0x40000000) where JSC expects -1/pointer.

CODEX TBSKIP WORKAROUND IS NOW SUSPECT (irqdesc.c ~445-446)
  On a #PF at 0x6056F06 with a slot value of 0xffffffffffffffff it does
  write_user_u64_for_exc(slot,0) and advances RIP. But 0xffffffffffffffff is a
  LEGITIMATE JSC empty/sentinel, not corruption. Zeroing it can damage these
  tables. The fault at 0x6056F06 (deref of -1 as a pointer) has a real upstream
  cause; skipping+zeroing hides it and may create the very inconsistency that
  later hangs the probe at 0x60CCF10.
