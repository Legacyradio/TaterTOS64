THE ROOT CAUSE (proven, fixed)
  Repurposed the DR watchpoints to the JSC hash-set bucket array and caught the
  init write:
    rip=0x6FFFFFD72A12 (libc __memset_avx2)  rdi=0x6FBBFFF11000  rdx=0x220
    rsi=0x00000000000000FF   -> JSC called memset(buckets, 0xFF, 0x220)
    BUT the bytes that landed were 0x00.
  i.e. an AVX memset asked to fill with 0xFF wrote 0. The kernel was CLOBBERING
  the interrupted user thread's YMM register mid-memset:
    - sched.c XSAVE/XRSTORs FPU state only on FULL CONTEXT SWITCHES, not on
      same-process interrupts.
    - Makefile CFLAGS had NO -mno-sse/-mno-avx, so GCC -O2 emitted SSE/AVX in
      kernel interrupt-path code (memcpy/memset/struct copies). A timer IRQ
      landing inside libc's AVX memset ran vectorized kernel code, trashed
      ymm0, and on iretq the memset resumed with ymm0=0 -> wrote zeros.
  Effect: JSC's -1 (0xFF) empty sentinels became 0 -> hash probe at 0x60CCF10
  never found an empty bucket -> infinite spin -> main thread hung holding the
  JSC heap lock -> workers starved. ALL prior symptoms (0xff/0x40000000 "corrupt"
  slots, TBSKIP, the 0x63ad6e0 futex "deadlock", the liveness hang) were this.

THE FIX
  Makefile: add -mgeneral-regs-only to kernel CFLAGS (kernel never touches
  x87/MMX/SSE/AVX; verified no float/double/intrinsics in kernel .c). Full kernel
  rebuild (rm src/kernel src/drivers *.o; make kernel). Compiles clean.
