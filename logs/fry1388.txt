LEGIT-vs-GARBAGE: DECISIVELY GARBAGE
  Raised the main-stack grow cap 64MB->512MB + bucketed TBBIGFRAME depth logging.
  Result: the zero loop walked the FULL 512MB to the new cap and faulted again
  (CR2=0x7FFFDFFFFFF8 = USER_VA_TOP-512MB-8). It is UNBOUNDED -> not a legit JSC
  reservation. (rsp stays pinned the whole walk; the loop decrements rdx, not rsp.)

DISASSEMBLY of 0x3F4CFB6 (JSC JIT-compiled function prologue)
  3f4cf96: mov 0x10(%rbp),%rsi   ; rsi = CodeBlock      (CallFrame[+0x10])
  3f4cf9a: mov 0x14(%rsi),%eax   ; eax = CodeBlock->m_numCalleeLocals
  3f4cf9d: shl $0x3,%rax         ; *8 = frame bytes
  3f4cfa1: neg %rax ; 3f4cfa4: add %rbp,%rax   ; newSP = rbp - size
  3f4cf58/5c: rdx=[CodeBlock+0x48]=VM ; cmp newSP,[VM+0x60] (soft stack limit)
  3f4cfa7: mov %rsp,%rdx ; 3f4cfaa: mov %rax,%rsp ; newSP committed
  3f4cfad: cmp %rdx,%rsp ; je done
  3f4cfb2: sub $8,%rdx ; 3f4cfb6: movq $0,(%rdx) ; jmp   ; zero locals down
  -> If numCalleeLocals is too SMALL (0) while old_rsp<rbp (callee-saved already
     pushed), newSP=rbp>old_rsp and the loop decrements rdx forever -> runaway.

CODEBLOCK DUMP (irqdesc.c fry1389 one-time dump on first deep stack fault)
  TBBFDUMP rip=0x3F4CFB6 rbp=0x7FFFFFFE2570 cb=0x6FBFF50F42C0 numLocals=0x0
           vm=0x6FBFF5400000 softLimit=0x7FFFFFB02FC0 ret=0x3F6817C
           callerfp=0x7FFFFFFE2630
  - cb = 0x6FBFF50F42C0 -> VALID JSC heap pointer (0x6f.. gigacage).
  - callerfp 0x7FFFFFFE2630 > rbp -> valid ascending frame chain (rbp/cb real).
  - softLimit 0x7FFFFFB02FC0 -> SANE (~5MB below stack top). Our stack reporting
    is NOT the bug; JSC's overflow guard is fine.
  - numLocals = 0  <-- THE CORRUPTION. A live function's CodeBlock cannot have 0
    callee locals here. The numCalleeLocals field ([cb+0x14]) has been ZEROED on
    the heap while the CodeBlock is still live -> prologue computes a 0-size frame
    -> infinite downward zero loop -> stack walk-off.

DIAGNOSIS
  HEAP CORRUPTION: a live JSC CodeBlock's numCalleeLocals field is zeroed. Same
  CLASS as the fry1385/86 #GP (intra-heap UAF/aliasing in the 0x6f.. cage). The
  fry1386 MADV_DONTNEED-zeroing fix is range-correct (page-aligned, end rounded
  up exactly like Linux madvise; clamps to region intersection — syscall.c:2432
  + 4573), so DONTNEED is NOT over-zeroing. The zeroing of this page comes from
  a DIFFERENT vm op or an allocator aliasing bug (mmap/munmap/mremap/MADV_FREE/
  brk handing the CodeBlock's page to two objects, or unmapping it so a later
  read demand-faults a fresh zero page).
