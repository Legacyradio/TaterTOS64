NEW RESULT — fry1388's hypothesis is RULED OUT
  fry1388 NEXT#1 was: "trace every vm op (dontneed/MADV_FREE/munmap/mremap/brk)
  whose range covers the CodeBlock page; find the op that zeros/unmaps the live
  page." The trace infra is already wired:
    - g_tb_target_page = 0x6FBFF50F4000 (syscall.c:83) — ALREADY armed to the cb
      page (committed). tb_log_vm_touch (syscall.c:2459) logs TBVMTOUCH for
      dontneed/unmap/release whose range covers g_tb_target_page, gated to tgid 3.
    - syscall.c:3498 logs "demand-refault" when the target page demand-faults.
  In this boot (trace ARMED, correct page): **0 TBVMTOUCH lines, 0 demand-refault
  lines for the cb page.** => Before the crash, NONE of dontneed / unmap / release
  / demand-refault touched the CodeBlock page. fry1388's leading suspects are
  INNOCENT for this corruption.

REVISED HYPOTHESIS (numLocals zeroed via a path NOT yet traced)
  Candidates, in rough priority:
  1. mmap/mremap ALIASING: a later anonymous mmap (or mremap move) is handed a
     physical page that still backs the live CodeBlock's page (kernel vm
     bookkeeping returns an overlapping/!committed slot — cf. TBVMREG "old-256
     ceiling / aliasing bug" note at syscall.c:2205). A zero-init of the new
     mapping then zeroes cb+0x14 through the alias. NOT covered by tb_log_vm_touch
     (which only watches dontneed/unmap/release).
  2. A second VA mapping the same PA (shared/file map, or a TBridge fd mmap) whose
     write lands on the CodeBlock page.
  3. The field was never written non-zero: a CodeBlock copy/relink/relocation in
     JSC that our loader/relocation handling truncated (less likely — cb+0/+8/+10
     look structurally valid; only +0x14 is 0).
