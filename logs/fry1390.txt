WHY THIS TEST
  Code audit before the test found two real SMP coherency holes:
  (a) NO cross-CPU TLB shootdown exists anywhere in the kernel — every invlpg
      in src/kernel/mm/vmm.c is local-only, and vmm_unmap_user (vmm.c:399)
      only invalidates even locally when the current CR3 matches the target
      address space. No IPI infrastructure beyond INIT/SIPI startup exists.
  (b) lx_try_demand_page (proc/syscall.c:3492) is check-then-map with no lock:
      two CPUs faulting the same VA can double-install frames (the "Lost a
      race ... Fine" re-check is not atomic with the install), and lx_map_one
      maps the PTE PRESENT+WRITE *before* zeroing the frame through the
      physmap window.
  Hypothesis: stale TLB entry on the second CPU -> writes land in a freed,
  reallocated frame -> precise small corruption on a page no VM op touched
  (which would explain fry1389's zero TBVMTOUCH hits). Cheapest decisive test:
  boot identical artifacts with -smp 1. If the crash vanishes, SMP coherency
  confirmed; if it persists, falsified.

CONCLUSIONS
  1. The corruptor is CPU-count-independent. NOT (solely) missing TLB
     shootdown, NOT the SMP demand-install race.
  2. Holes (a)+(b) above are still real architectural bugs that must be fixed
     before -smp >1 is trustworthy, but they are NOT this crash. Deferred.
  3. Since the page's PTE/PA never changes and no VM op covers it, the
     numCalleeLocals=0 dword was produced by a WRITE through some live
     mapping: user-mode (JIT/interpreter store to a stale/aliased pointer)
     or kernel-mode through the physmap window (stray write-to-user such as
     clear_child_tid zeroing, futex WAKE_OP store, or a zero-fill of a
     double-allocated physical frame). The existing TBWATCH debug-register
     handler only fires for CPL3 hits (irqdesc.c:482) — kernel-mode writes
     are currently INVISIBLE to it.
