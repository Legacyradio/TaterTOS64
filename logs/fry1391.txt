STEP 3 — REAL KERNEL BUG FOUND + FIXED (per-CPU callee-saved scratch)
  WHY suspected: hit pattern = object freed while reachable = lost GC root;
  JSC's GC signal-suspends threads and conservatively scans the ucontext
  register set. Audit of the delivery path found:
  - syscall_entry snapshotted user rbx/r12-r15 into PER-CPU gs:24..56.
    Any other thread's syscall on that CPU overwrites them. A thread blocked
    in futex_wait (= where GC-suspended threads sit) therefore got ANOTHER
    THREAD's callee-saved regs in its signal ucontext (lx_deliver_signal_on_
    sysret read gs slots at sysret time). Conservative roots living only in
    those regs are lost.
  - rt_sigreturn wrote callee-saved restores back to gs slots that NOTHING
    ever read -> dead stores; handler-modified ucontext callee-saved regs
    were silently dropped.
  FIX (in tree):
  - syscall_entry pushes rbx/r12-r15 into the PER-THREAD kernel stack frame
    (frame grows 12 -> 17 slots; new LX_SYSFRAME_R15..RBX=12..16, _SLOTS=17;
    lx_syscall_frame updated).
  - syscall exit restores the 5 regs from the frame (rbp-relative 32..64) —
    makes rt_sigreturn modifications actually reach the registers.
  - lx_deliver_signal_on_sysret, lx_rt_sigreturn_sys, clone3 all converted
    from gs slots to frame slots; lx_read/write_gs_slot deleted; gs:24..56
    stores removed from syscall_entry.
  This bug is REAL and could corrupt any threaded Linux app under signals;
  fixing it is required regardless of the present crash.

STEP 4 — REGRESSION + FIX (clone3 hardcoded frame depth)
  First boot after Step 3: pid 3 (first clone3 child) died vec=1 SIGTRAP at
  rip=0x287a9b1, r13-r15 = raw x86 code bytes, TF set in rflags. Cause: the
  clone3 case computed the frame base itself with a HARDCODED
  kernel_stack_top - 12*8 (missed in Step 3) -> all child-inherited regs
  read 5 slots off. Fixed: clone3 now uses lx_syscall_frame() +
  LX_SYSFRAME_RIP/RSP names. Swept the tree: no other hardcoded depth.

STEP 5 — RE-TEST: crash persists, root cause is UPSTREAM
  Boot with Steps 3+4: clone3 children fine, thread pool up, TBWATCHARM,
  HIT 1 (=6) and HIT 2 (=0, rdx=0) IDENTICAL to before (same rsp values
  even). So the gs-scratch bug was NOT the corruptor of this particular
  field; the zero is faithfully copied from an already-corrupt source.
  Determinism (same addresses/rsp every boot, smp-independent) now points
  AWAY from GC races toward a deterministic upstream zeroing of the source
  object in the 0x6FBB.. region (candidates: bytecode-cache deserialization
  divergence, madvise/DONTNEED zero semantics on the source page, vm-region
  bookkeeping aliasing).
