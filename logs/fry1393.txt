HOW MEMORY-CORRUPTION WAS CONCLUSIVELY EXCLUDED (fry1390-1392, recap)
  - The CodeBlock zero is a COPY (instr 0x4C84308) of an already-zero SOURCE
    UnlinkedCodeBlock (r8). The kernel never writes the field (0 CPL0 #DB hits).
  - Source page: ONE eager 32MB mmap (0x6FBBF8000000 len 0x2000000), NO vm op
    ever touches it (0 dontneed/unmap/fault on the page), and a FULL user
    page-table walk finds NO second VA mapping its PA (no aliasing anywhere).
    => the body bytes were never overwritten/aliased: the object was simply
    read before it was fully constructed (use-before-init).

THE SAFEPOINT VIOLATION (this session's evidence)
  - sig 30 = JSC's stop-the-world GC thread-suspend signal. The GC thread is
    pid 3 (sender=3 on every TBSIG queue; pid 3 also owns all 442 sweep
    MADV_DONTNEED in TBVMTOUCH).
  - sig 30 is delivered ONLY to pid 4 and pid 8 (TBSIG: 52x target=8, 2x
    target=4). It is NEVER queued or delivered to pid 2 (0 "deliver pid=2
    sig=30"). pid 2 is the MAIN MUTATOR and is the thread that does BOTH the
    good and the bad copy AND takes the fatal fault.
  - pid 2's syscalls right up to the crash include epoll_pwait rc=0xffffffea
    (-EINVAL) REPEATEDLY. Our epoll_pwait is effectively unimplemented and
    returns EINVAL immediately, so pid 2 NEVER actually blocks — it spins in
    the event loop in userspace. JSC/Bun treats a thread in the event loop as
    parked/at-safepoint; the GC therefore does not stop it, and our kernel,
    delivering signals ONLY at syscall/fault boundaries, could not preempt it
    anyway.
  - Result: pid 3 runs stop-the-world (suspends 4 & 8, sweeps with DONTNEED)
    while pid 2 keeps allocating/initializing objects in the same heap. pid 2
    reads an UnlinkedCodeBlock that the concurrent sweep freed or that pid 2
    itself had only partly built when the collector recycled its cell ->
    numCalleeLocals=0 -> JIT prologue frame size 0 -> stack walk-off -> crash.
  - Deterministic on -smp 1 because the spin/sweep interleave is scheduler-
    deterministic; smp-independent because it's a logical safepoint race, not
    a hardware memory-ordering race.

WHY THIS SESSION'S TWO KERNEL FIXES DID NOT CURE IT (but are still correct)

    per-thread frame slots; signal ucontext now exposes correct rbx/rbp/
