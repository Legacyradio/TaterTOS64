THE REFRAME (fry1414 boot trace — decisive)
====
- LXEPCTL beacon: ZERO lines. The DNS socket is NEVER registered with
  epoll. So the send is NOT gated on epoll/poll readiness. (epoll
  close-purge from fry1413 kept — correct Linux semantics — but it was
  not the blocker.)
- pid=5 sequence around the DNS connect (serial /tmp/s.log this boot):
    LXSOCK socket pid=5 domain=2 type=0x80802 -> fd=17
    LXCONN  pid=5 fd=17 fam=2 dst=10.0.2.3:53 alen=16 rc=0
    TBFUTEX wait-begin pid=5 uaddr=0x62661cc expected=1 timeout_ms=10000
    TBFUTEX wait-return pid=5 uaddr=0x62661cc rc=0 elapsed=4819 (woken)
    ... then repeats the 10s idle wait.
- 0x62661cc is in the exe RW PT_LOAD (data/GOT) = a libuv THREAD-POOL
  work-queue semaphore. pid=5 is a libuv worker; after connect it goes
  back to IDLE (waiting for the next work item), woken periodically.
- => getaddrinfo() on the worker RETURNED (or aborted) immediately after
  connect(), WITHOUT ever sending a DNS query. No send syscall of any
  kind (sendto/send/sendmsg/sendmmsg/write) fires from ANY pid the whole
  boot (LXUDP count = 0). connect() to 10.0.2.3:53 returns 0 cleanly.

WHAT THIS RULES IN/OUT
====
- NOT epoll, NOT poll readiness, NOT our send path (never reached).
- The bail is between connect() and the first send INSIDE the resolver.
- SYS_CONNECT DGRAM is fine: assigns ephemeral local_port, sets
  remote_ip/remote_port, state=CONNECTED, rc=0 (verified syscall.c ~885).
  So getsockname()-returns-port-0 is NOT the cause (local_port is set).
