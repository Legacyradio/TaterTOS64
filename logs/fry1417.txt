ROOT CAUSE (one bad constant)
====
- syscall.c:322  #define FRY_POLLOUT 0x0002u
- Linux poll ABI: POLLIN=0x1, POLLPRI=0x2, POLLOUT=0x4.
  -> kernel 0x2 is Linux POLLPRI, NOT POLLOUT.
- poll_check_fd() DGRAM branch DOES set "always writable" — but as 0x2.
  lx_poll_fds masks revents &= events|ERR|HUP|NVAL = 0x4|0x8|0x10|0x20:
  0x2 & 0x3C = 0 -> n=0 -> poll returns 0 -> glibc never sends.
- ALL other kernel poll bits match Linux (IN=1 ERR=8 HUP=10 NVAL=20).
  fry1397's "fry/Linux poll bits identical" was wrong for exactly one
  bit, and that bit is the one send_dg lives on.
- Corroboration: the OS's OWN user libc (src/user/libc/fry.h:429)
  defines FRY_POLLOUT 0x0004 — kernel/userspace were already internally
  inconsistent; native poll(POLLOUT) callers had the same latent bug.
- Why nothing caught it earlier: Bun's uSockets uses EPOLL, and the
  epoll path has explicit translators (syscall.c:3965/3974 LX_EPOLLOUT
  0x4 <-> FRY_POLLOUT) so TCP readiness worked; only the plain
  poll/ppoll path exposes raw FRY_* bits to a Linux caller. The DNS
  resolver is the first plain-poll POLLOUT consumer.
- This also retroactively explains fry1414's "DNS fd never registered
  with epoll" (correct — glibc uses poll) and why the worker "returns
  to idle without sending" (send_dg exits on poll timeout).

FIX (fry1418, one line)
====
  FRY_POLLOUT 0x0002u -> 0x0004u (syscall.c:322).
  Audited all 17 use sites: all inside syscall.c; epoll translators

  native-libc expectation (0x4) now matched. No site stores the bit
  persistently, so no migration concern.
