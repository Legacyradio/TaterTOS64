ROOT CAUSE (from source, kernel/proc/sched.c)
====
The scheduler publishes a task as wakeable BEFORE its context is saved:

1. Block path: sched_block_futex() (and sched_block_poll/sched_sleep)
   sets p->state = PROC_WAITING + wait key under g_sched_lock, then
   UNLOCKS and returns. The thread then reaches sched_tick() to switch
   away. Its kernel context (saved_rsp) is NOT yet saved — that happens
   only inside context_switch().
2. Switch path: sched_tick() picks `next` and sets current[cpu] under
   g_sched_lock, then RELEASES the lock, and only afterwards runs
   context_switch(cur, next) — which is what finally writes
   cur->saved_rsp (sched.c:929; save at sched.c:288ff).
3. Race: between (1)'s unlock and (2)'s save, another CPU's
   sched_futex_wake / sched_tick timeout pass sees the thread WAITING,
   wakes it (wake_runnable_locked), picks it, and context_switch loads
   its STALE saved_rsp from a previous block — while the first CPU is
   still executing on that thread's real kernel stack and is about to
   overwrite saved_rsp. Two CPUs on one kernel stack -> frame
   corruption -> wedge with IRQs off -> timer dead -> 'now' frozen ->
   every timed wait sleeps forever. Matches every observable.

   On -smp 1 the window is closed by cli (irq_save_disable spans the
   whole block+switch sequence on the only CPU), which is why ~1400
   single-core boots never hit it. This is exactly the class of bug the
   multicore directive (fry1421, recorded policy) was meant to surface.

   Note fry1419/1420's -smp 1 TLS starvation plus this -smp 2 race
   means NEITHER config was sound: single-core starved a TLS thread to
   death; multicore exposes the unsaved-context race. The race is the
   real bug; fix it, stay multicore.

EOI/timer exonerated: LAPIC timer is periodic mode (lapic_timer.c),
EOI is sent as chip->ack BEFORE the handler (irqdesc.c:781-783), so a
missing EOI is not the freeze mechanism. kprint_serial_only locking is
consistent (g_sched_lock -> kprint_lock only, no inversion).

FIX DIRECTION (fry1423)
====
Linux-style "on_cpu" gate, minimal form:
- Add volatile on_cpu flag to struct fry_process. A task's on_cpu stays
  1 from the moment it is picked (under g_sched_lock) until
  context_switch has finished saving its outgoing context (cleared in
  the switch asm immediately after the rsp store, before loading the
  new rsp — x86 TSO orders the two stores).
- sched_tick must never switch to a candidate with on_cpu==1 (another
  CPU still owns its stack); rotate/skip it for this tick — it is
  eligible 1ms later.
- to->saved_rsp must be loaded into a register BEFORE clearing
  from->on_cpu (after the clear, the old stack can be stolen
  immediately; no memory operand may reference it).
- Init: boot contexts and whichever task is currently running get
  on_cpu=1; fresh tasks 0.
