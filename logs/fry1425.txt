THE OUTPUT BUG (root cause, host-verified)
====
Host strace of the SAME binary (2.1.172, claude -p):
    fcntl(1, F_DUPFD_CLOEXEC, 0) = 12
    write(12, "Hello from TaterTOS ...", 208) = 208   <- THE REPLY
Bun dups stdout to a high fd and its async writer emits ALL output
through the dup (fd 15 = writer eventfd). It NEVER writes fd 1 raw.
TaterTOS: process_launch_linux installs NO fds; lx_dup_fd_at's
validity check `!fd_is_open(shared, oldfd)` rejected oldfd=1 with
-EBADF BEFORE reaching its own `oldfd <= 2` stdio-dup branch (dead
code — the design intended stdio dups to work). Result: Bun's writer
holds a dead fd; replies, errors, EVERYTHING silently dropped, every
run. Important: TBTRACE ret only logs FAILING syscalls (all observed
rc's negative) — successful writes were never visible, which hid this.

FIXES LANDED (in tree, syscall.c, tag fry1426)
====
1. lx_dup_fd_at: fds 0-2 always pass validity (kernel console backs
   them) -> the existing FD_STDIO dup branch is live again.
2. LNX_dup2: same validity fix (its oldfd<=2 branch was equally dead).
3. fcntl F_GETFL on uninstalled stdio fds returns O_RDWR (0x2) to
   match Linux console fds (host-verified) — a zeroed table entry
   reads as O_RDONLY and can mislead runtime writability checks.
   fd 0 (stdin) deliberately left uninstalled otherwise — current
   stdin probing behavior is what claude already works against; not
   risking a blocking-read regression.
