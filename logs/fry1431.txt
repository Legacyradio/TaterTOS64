stall is UPSTREAM of them. Per-connection counters show exactly ONE

three connections) — so the next session starts at the NIC receive
ring / IP demux, not the TCP state machine.

- Each TLS connection delivered ONE full-MTU segment to tcp_process,
  in order (delta==0), then silence. No out-of-order drops, no
  retransmit overlaps. The fry1430 "mid-response stall" is real but
  it is NOT a TCP sequencing problem — segments simply stop being

- claude consequently never receives a complete response, waits out

  end-state as every prior boot; now localized one layer lower.

LANDED THIS STEP (in tree, netcore.c — KEEP, all correct)
====
- RFC 793 overlap trimming in TCP_ESTABLISHED: signed seq-delta;
  retransmits that overlap already-acked data get the received prefix
  trimmed and the remainder accepted, instead of the old exact-match
  `seq != ack_num` drop that would wedge a stream permanently on any
  partial-accept. (Did not trigger this run, but removes a real
  latent wedge.)
- Honest advertised receive window: real ring free space capped at
  65535, replacing the hardcoded 65535. (Ring is 1MB so not the
  current limiter, but the old advert was dishonest under burst.)
- Per-conn uncapped counters dbg_in_segs/in_bytes/drop_ooo/trimmed +
  TBTCP rx/drop/trim beacons. Old 3-line-global TCP_RX beacon REMOVED
  (it produced false "only 3 packets arrived" conclusions for days).

NEXT SESSION STARTS HERE — NIC RECEIVE RING (driver-level)
====
Hypothesis: the e1000 RX descriptor ring stops yielding frames after
the first per flow — classic causes on this driver class:
  1. RX descriptor not handed back to the NIC after consumption (tail
     register RDT not advanced / wrapped) -> ring fills, NIC drops
     silently. Check e1000 RDT update in the RX poll path.
  2. RX head/tail wrap or off-by-one so only the first descriptor of
     each batch is read.
  3. NET_POLL pump cadence: frames land in the ring but the poll that
     drains them into IP/TCP runs too rarely under the -smp 2 idle
     loop (epoll_pwait2 park). NET_POLL totals WERE climbing in
     fry1430, so frames do keep arriving at the device — favors (1).
INSTRUMENT: per-RX-descriptor beacon in the e1000 driver (rx index,
RDH/RDT, descriptor status/length) + an IP-demux counter (frames
delivered to tcp_process vs udp). Diff "frames the NIC received"
against "segments tcp_process saw". The gap names the layer.
Files: src/drivers/net/e1000.c (RX ring), netcore.c ip_input/
tcp_process. KEEP fry1431 TBTCP counters — they are the TCP-side
ground truth for the diff.
