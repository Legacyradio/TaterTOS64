WHY THIS STEP (rule 6)
------------------------------------------------------------------------
fry1431's verdict ("exactly one segment accepted per connection") was
OVERSTATED by its own sampling: the TBTCP rx print fired only when
(dbg_in_segs & 0xF) == 1 — i.e. at segment 1, then dark until segment
17. So "segs=1, no later line" only proves the true count is 1..16.
Worse, the fry1431 serial log shows NET_POLL rx=12 frames per poll
ARRIVING AFTER the last TBTCP line — the NIC kept delivering while TCP
went quiet, but every tracer between them was capped (IP_RX: 5 prints,
NET_POLL: 10 prints) and went dark exactly when the stall window opened.
Inspection of e1000_rx_poll, net_rx, ip_process, and tcp_process found
no bug by reading: RDT recycling is correct, demux has no caps, conn
lookup is sound. This is now strictly a measurement problem.

CHANGES (all diagnostic; strip with the other beacons before release)
------------------------------------------------------------------------
src/drivers/net/e1000.c
  - File-scope prototype for kprint_serial_only (was block-local in the
    TX tracer; new call sites need it).
  - e1000_rx_poll: TBE1K beacons. Uncapped delivered-frame counter
    (prints every 8th: "TBE1K rx total= len="), and — new visibility —
    an ALWAYS-printed drop line for any descriptor the loop refuses
    ("TBE1K DROP n= eop= err= len="). err / missing-EOP / zero-len
    refusals were previously silent and are a live suspect for frames
    vanishing between the NIC and net_rx.

src/drivers/net/netcore.c
  - ip_process: replaced the 5-print-capped IP_RX tracer with an
    uncapped TCP-forward counter ("TBIP tcp_fwd= len=", every 8th).
  - struct tcp_conn: added dbg_frames — counts ALL segments matched to
    the conn (any flags, any state). The diff dbg_frames vs dbg_in_segs
    separates "segments stopped reaching tcp_process" from "segments
    reached the conn but were not accepted as data".
  - tcp_process: dbg_frames++ on every conn match; RST arrivals now log
    ("TBTCP RST conn= state= frames=") — a server-side RST silently
    killing the conn would have been invisible before.
  - tcp_process ESTABLISHED: TBTCP rx now prints EVERY accepted segment
    (sampling removed — see WHY).
  - tcp_send_segment: TBTCP tx beacon (first 64 sends + every 32nd):
    flags, ack number, advertised window, payload len. If our ACKs
    stop, go stale, or starve the window, slirp stops sending and the
    stall is ours — this line is the proof either way. Conn index is
    bounds-guarded because RST replies use a stack dummy conn.
  - net_poll: TBDUMP quiescence dump every 4096 polls — full live conn
    table (state, frames, segs, bytes, ooo, trims, unread ring bytes).
    After the stall the event beacons go silent; this dump carries the
    final per-conn truth in the post-stall serial log regardless.

WHAT THE NEXT BOOT'S LOG WILL SETTLE
------------------------------------------------------------------------
Read the post-stall window and diff adjacent layers:
  TBE1K total      vs TBIP tcp_fwd   -> frames dying in net_rx/ip_process
  TBE1K DROP lines                   -> NIC handing us bad descriptors
  TBIP tcp_fwd     vs TBDUMP frames  -> segments missing the conn lookup
  TBDUMP frames    vs TBDUMP segs    -> data refused inside the handler
  TBTCP tx ack/win                   -> our ACKs stale or window starved
  TBTCP RST lines                    -> server killed the conn, not us
One of those diffs must be nonzero at the stall boundary; that diff is
the fry1433 fix target.
