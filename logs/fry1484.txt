NEXT BLOCKER REVEALED (epoll_pwait2/timerfd busy-spin)
------------------------------------------------------------------------
Two consecutive 64-slot end-to-end runs (c fresh image, d reused image)
hung BEFORE session init. Tail = pid 14 spinning:
  LXDNS pid=14 nr=441 (epoll_pwait2) rc=1   <- 1 fd reported ready
  LXDNS pid=14 nr=0   (read) a3=8 rc=8       <- drains 8B timerfd/eventfd
  ...forever.
Confounds RULED OUT:
  - OAuth: token had 33-67 min left at run time (checked expiresAt). Not
    expiry.
  - Network: DHCP OK, TCP connect 443 OK, claudeai-mcp "Fetched servers"
    COMPLETED in all 3 runs (incl. the hung ones). Not the mcp fetch.
  - 64 structurally: every FRY_SOCK_MAX use is a plain `< FRY_SOCK_MAX`
    loop bound (scales); no 16-width mask/buffer. The only behavioral
    delta vs 16 is that socketpair no longer fails -> claude proceeds
    further.
INTERPRETATION: at 16, socketpair ENFILE forced claude onto a degraded
path that happened to complete; at 64 it gets all its pairs and enters a
fuller path that hits a kernel epoll_pwait2/timerfd readiness bug ->
epoll keeps reporting the timerfd ready, the 8-byte read drains it, epoll
immediately re-reports ready -> infinite poll, never blocks, never
advances to init. This is the SAME "fix N reveals N+1" pattern as
ENFILE->EBADF. The socket fix STANDS.
