=== WHAT IS / IS NOT ROOT-CAUSED ===
PROVEN: pid14 is a DNS/net worker; its wedge state = no DNS sockets + silent eventfds + timerfd-
only spin; the API response (90KB) was received and read; success completes via main-loop eventfd
signaling that the deadlock lacks.
NOT YET PINNED (single line/root): WHY pid14 ends up with nothing to do but the timer, and what
it (or the main thread) is ultimately waiting for. Two concrete candidates, both TESTABLE:
  (C1) Lost cross-thread wakeup: eventfds fd=7/9/16 are pid14's work-signal from other threads.
       They go silent at the wedge. If a thread SHOULD write one of them (to hand pid14 the next
       DNS job or to tell it to park) and doesn't — that is the lost signal. poll_check_fd treats
       eventfd readable only when counter>0 (syscall.c:1004); a write that never happens => never
       ready. Need: log every LXEVFD wr (target fd + writer pid) in the wedge window and find the
       fd7/9/16 write that fires in SUCCESS but not in DEADLOCK.
  (C2) Spurious socket HUP: poll_check_fd reports POLLHUP for a TCP socket in state CONNECTED when
       tcp_is_connected()==false (syscall.c:972-973) and for SHUTDOWN/CLOSED (990-991). If a DNS
       or API socket is HUP'd prematurely (e.g. transient not-yet-connected, or fd-reuse race),
       libuv tears it down and the resolver/loop stalls. Need: tag each POLLHUP with the branch +
       sk->state + tcp_is_connected(), scoped to claude tgid.
