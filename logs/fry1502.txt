=== WHY pid5's BLOCK NEVER WAKES (the bug) ===
process_wait4 (process.c:1080) and process_thread_join (process.c:1031) both do:
   scan for target; if ZOMBIE/DEAD -> reap+return; if nohang -> return 0;
   set cur->wait_pid/wait_tid; cur->wake_time_ms = UINT64_MAX; sched_block(); sched_yield();
sched_block (sched.c:564) sets state=PROC_WAITING. The waker process_wake_pid_waiters
(process.c:1151) wakes procs with state==PROC_WAITING && wait_pid==pid. STATE MATCHES, so it is
NOT a static state-mismatch. It is a MISSED-WAKEUP RACE, fatal because the block has NO TIMEOUT:
  On -smp 4, between pid5's ZOMBIE/DEAD liveness check and sched_block setting PROC_WAITING, the
  target child can exit on another core → proc_free→process_wake_pid_waiters runs while pid5 is
  still PROC_RUNNING (not yet WAITING) → no match → wake lost → pid5 blocks on UINT64_MAX forever.
  The loop would re-poll on wakeup, but no wakeup ever comes and there is no timeout to retry.
Corroborating: kill→ESRCH at L16691 (claude signalling an already-gone child) + the ECHILD
errors (L13819 "Ripgrep first use test threw ... ECHILD") confirm claude is in the child-
management path here. This run is -smp 4 (race-prone). The fry1462 milestone was a simple sonnet
round-trip that never exercised the rg/threadpool spawn+reap path at this concurrency.

=== FIX DIRECTION (to implement next, pending one confirming instrumented run) ===
PROPER fix (not a band-aid): close the missed-wakeup race in process_wait4 AND process_thread_join.
Re-check the target's ZOMBIE/DEAD state AFTER transitioning to PROC_WAITING but BEFORE yielding,
under the scheduler lock (or arm the wait, then recheck the condition, then block) so that an exit
concurrent with arming cannot be lost. (Mirror the pattern sched_block_futex already uses:
compare-then-block atomically under g_sched_lock.) A bounded re-poll timeout would also self-heal
but is a band-aid over the real race — prefer the atomic arm+recheck.
