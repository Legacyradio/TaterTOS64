=== ROOT CAUSE (structural pin — as strong as observation can get here) ===
pid5 (main) hangs in a no-beacon blocking syscall (wait4 or SYS_THREAD_JOIN) right after kill->ESRCH
(fry1504 confirmed: no further pid5 activity, and pid5's only blocking wait4 had already returned).
process.c's process_wait4 (1080) and process_thread_join (1031) do their ZOMBIE/DEAD predicate
check WITHOUT any lock, then call sched_block (which sets PROC_WAITING under g_sched_lock) and block
on wake_time=UINT64_MAX (NO timeout). The waker proc_free->process_wake_pid_waiters (process.c,
also NO lock) sets state+wakes. g_sched_lock is STATIC to sched.c — process.c CANNOT synchronize
with it. So there is a genuine unsynchronized window: waiter sees target alive -> (child exits on
another core: marks DEAD + wakes, but waiter not yet PROC_WAITING) -> waiter blocks forever. On
-smp 4 this is hittable; ANY added serialization closes the window (hence the Heisenbug).

=== THE FIX (path A — close the race; NOT the band-aid timeout) ===
Synchronize the wait/exit paths through g_sched_lock via new sched.c helpers (process.c can't touch
the static lock directly):
  1. sched.c: sched_pidwait_exit(pid, state, code) — under g_sched_lock: set procs[pid] state+exit
     code THEN wake all PROC_WAITING with wait_pid==pid. proc_free calls this for the mark-dead+wake.
  2. sched.c: sched_pidwait_arm(caller_pid, target_pid) — under g_sched_lock: if target is
     ZOMBIE/DEAD return 1 (reap, don't block); else arm caller PROC_WAITING+wait_pid and return 0.
     process_wait4/process_thread_join call this for check-and-arm, then yield only on 0.
Both sides under the SAME lock => the exit either is seen by the arm (reap) or arms-before-exit
(wake hits the WAITING waiter). Provably race-closing (not merely timing-shifting), so it is a real
fix, distinguishable from a perturbation-mask.
