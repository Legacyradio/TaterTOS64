=== ROOT CAUSE (from fry1500-1505) ===
The sock=64 / -smp4 deadlock (9/9 runs fry1491-1499) was a missed-wakeup RACE in the pid-wait
(wait4) path. claude's main thread (pid5), after a kill->ESRCH on an already-gone rg/sh subprocess,
calls wait4 to reap it. process_wait4 (process.c) checked the child's ZOMBIE/DEAD state with NO
lock, then blocked on an INFINITE wait (wake_time=UINT64_MAX). The waker, proc_free, marked the
child DEAD + woke PROC_WAITING pid-waiters also with NO lock — and g_sched_lock is private to
sched.c, so process.c could not synchronize. On -smp4 the child's exit could land between the
waiter's check and its block => the wake found no PROC_WAITING waiter and was lost => pid5 hung
forever => its threadpool/JS workers all parked (62661cc etc.) => whole-process freeze (only pid6
heartbeat + a subprocess continued). Confirmed Heisenbug: ANY added serialization (serial beacons
fry1503, or fxr_rec_sys taking g_sched_lock fry1505) shifted timing and the run SUCCEEDED instead
(2/2 instrumented green vs ~10/10 uninstrumented deadlock) — the signature of a tight wake/wait race.

=== THE FIX (close the race; both sides under g_sched_lock) ===
sched.c (new helpers, declared in sched.h):
  - sched_pidwait_arm(caller, target): under g_sched_lock, re-check target reapable; if ZOMBIE/DEAD/
    gone return 1 (caller re-loops to reap, does NOT block); else atomically arm caller PROC_WAITING
    (wait_pid=target, UINT64_MAX) and return 0 (caller yields). Mirrors sched_block's
    remove_from_runqueue + by-pid fallback for the running-task case.
  - sched_pidwait_exit(target): under g_sched_lock, mark target DEAD + wake its PROC_WAITING
    pid-waiters via wake_runnable_locked.
process.c:
  - process_wait4: replaced the unlocked check + sched_block with: if (sched_pidwait_arm(cur,pid))
    continue; else sched_yield(). The loop's top re-scan reaps when woken.
  - proc_free: replaced the inline unlocked "set DEAD + scan/wake pid-waiters" with
    sched_pidwait_exit(pid). (wake_joiners + the rest of teardown unchanged.)
Both sides now serialize on g_sched_lock => the exit is either SEEN by the arm (reap, no block) or
lands AFTER the arm (wake hits the PROC_WAITING waiter). PROVABLY race-closing — so post-fix greens
reflect the fix, not perturbation luck. Scoped to the pid-wait/wait4 path only; SYS_THREAD_JOIN
left as-is (claude uses futex-based pthread_join, not the native join).
