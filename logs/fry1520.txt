fry1520 - Chunked Linux ELF streaming and visible Claude loading state
Date: 2026-06-15 11:39:14 CDT

Why:
  The restored GUI Shell now delivers the typed "claude" command to the
  kernel, but the user-visible Shell appears frozen because
  fry_spawn_linux_args() is synchronous. It does not return a pid until
  process_launch_linux() finishes elf_load_linux() for the 250,480,336-byte
  /nvme/RCLAUDE.LXE image.

  Serial evidence from the headed GUI runs showed the command path was alive:
    LINUXELF: load start /nvme/RCLAUDE.LXE
    LINUXELF: open /nvme/RCLAUDE.LXE
    LINUXELF: size /nvme/RCLAUDE.LXE 250480336

What changed:
  src/kernel/proc/linux_elf.c
    - Added lx_stream_to_user(), a bounded bounce-buffer streaming helper.
    - Streamed PT_LOAD reads now use up-to-1 MiB chunks, with fallback to
      smaller chunks if contiguous pages are unavailable.
    - Large segment streaming prints serial progress every 16 MiB.
    - The existing segment-cache behavior remains enabled so later Claude
      self-reexec / embedded-rg loads do not regress.

  src/user/shell/shell.c
    - cmd_claude() now prints and renders:
        claude: loading /nvme/RCLAUDE.LXE...
      before entering the synchronous Linux-spawn syscall.

Current result:

  reaches the loader, improving streamed VFS read size, and rendering a visible

Remaining blocker:
  Claude is not yet confirmed interactive from the GUI Shell. The first desktop
  launch still pays the synchronous eager-load + segment-cache fill cost before
  Shell gets a child pid and can pump child stdout/stdin. The next fix should
  either move Linux launch off the Shell UI path or change the initial/cache
  load policy without regressing the later embedded-rg self-reexec cache.
