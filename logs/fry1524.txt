fry1524 - FIX + VERIFIED: child fd0 blocking read (no more EOF-129 exit); Claude stays interactive
Date: 2026-06-15 13:12:08 CDT

Type: CODE CHANGE + HEADED GUI VERIFICATION.
Implements the fix scoped in fry1523 (confirmed root cause: child fd0 read returned
EOF on empty stdin -> node/Ink ended stdin -> trust prompt exited 129).

Why (Rule 6):
  In the GUI interactive path, lx_read_fd(fd0) returned 0 (POSIX EOF) when the
  stdin ring (shared->inbuf) was empty. node read fd0 in blocking mode (it could
  not epoll-register stdin: epoll_ctl ADD fd0 -> EBADF, fry1523), so read()==0 was
  taken as end-of-stdin and Claude exited the trust prompt with code 129. A
  blocking read on an open stdin must block until data, not return EOF.

Change (src/kernel/proc/syscall.c, two sites; GUI path only, serial path untouched):
  1) lx_read_fd(), fd==0 GUI branch (~line 4665):
     Replaced "{ sched_yield(); return 0; }" with a cooperative blocking loop:
       - drain inbuf if data present (return bytes);
       - if fd0 is O_NONBLOCK (shared->fd_flags[0]): return -EAGAIN;
       - else sched_block_poll(cur->pid, UINT64_MAX) + sched_yield(), re-fetch
         cur/shared after wake, retry. Never returns 0 while stdin is open.
     Mirrors the FD_PIPE_READ blocking idiom in the native read path (~line 7972).
  2) SYS_PROC_INPUT handler (~line 8521):
     After writing keystrokes into inbuf, "if (nw > 0) sched_wake_poll_waiters();"
     so a thread parked in lx_read_fd(fd0) wakes when the Shell delivers input.
  Scope: only the Linux child's fd0 path changes. The Shell is a native FRY app
  (native read path), so its pump is unaffected. The non-GUI/serial branch
  (ps2_kbd_read ... return 0) is left exactly as-is to protect the validated
  serial/stream-json harness (fry1506) and Rule Zero.
