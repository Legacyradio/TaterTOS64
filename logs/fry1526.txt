Follows fry1525 (C1 parser built; blocked because child stdout went to the fb
console, not the Shell outbuf) and the user's E (master-pump output half) + the
load-time directive ("10-min load is unusable on a customer front").

Why (Rule 6):
  1) fry1525 root cause: lx_write_fd routed a Linux child's fd1/2 to kprint_write
     (kernel framebuffer console), so the Shell pump drained an empty outbuf and the
     C1 parser had no bytes. Need child stdout/stderr -> outbuf for GUI children.
  2) Load time: the 250MB eager-load took ~10 min. Root cause (this session):
     totfs_read_block read sectors ONE PER NVMe COMMAND, and totfs_read_file_data
     read ONE BLOCK at a time -> ~512k single-sector commands for the load. The
     bd->read interface already takes a sector count and nvme_io_rw splits/pipelines
     by mdts with PRP lists (build_prp walks per-page, so multi-page buffers are
     safe), so the per-sector/per-block loops were pure latency.

Changes:
  src/kernel/proc/syscall.c (lx_write_fd, fd1/2 branch ~line 4845)
    - GUI child (gui_process_running() && !process_name_is_gui(cur->name)): write
      fd1/2 bytes into shared->outbuf (block-until-space, no drops) so the owning
      GUI Shell pump (SYS_PROC_OUTPUT) renders them. Non-GUI keeps kprint_write
      (validated serial/stream-json harness untouched).
  src/user/shell/shell.c (pump_child_io)
    - Drain the child outbuf FULLY each tick (while fry_proc_output()>0) instead of
      one 256-byte slice, so a TUI repaint isn't throttled to 16KB/s.
  src/kernel/fs/totfs.c
    - totfs_read_block: one multi-sector bd->read of sectors_per_block (was a
      per-sector loop).
    - totfs_read_file_data: fast path reads the longest physically-contiguous run
      directly into the caller buffer in ONE multi-block bd->read; partial head/tail
      blocks keep the temp-buffer slow path.
