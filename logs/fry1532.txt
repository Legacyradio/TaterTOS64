ROOT CAUSE - fry1526 totfs_read_file_data fast path:
   The fast path does fs->bd->read(lba, out + total_read, run*sectors_per_block) -
   a direct NVMe DMA straight into the caller's buffer 'out'. nvme build_prp resolves
   the buffer with virt_to_phys over the KERNEL map.
   - ELF LOAD path: vfs_read reads into a KERNEL chunk buffer (lx_stream_to_user) ->
     virt_to_phys works -> DMA lands -> 250MB binary loads fine (why claude RUNS).
   - Claude RUNTIME file reads: lx_read_fd FD_FILE -> vfs_read(vf, dst, len) where
     dst is a USER virtual address (syscall.c ~4681). virt_to_phys can't resolve a
     user VA -> the DMA does not land in claude's buffer -> truncated/garbage read.
   The OLD code read each block into a kernel stack temp (blk[]) then CPU-copied to
   'out', which is correct for user buffers. My direct-DMA optimization broke that.

Scope: totfs_read_block's multi-sector change (also fry1526) is SAFE - it only ever
   receives the kernel stack 'blk' buffer. Only the totfs_read_file_data fast-path
   direct-DMA-into-out is unsafe.

Fix (next step, fry1533): keep multi-block speed but make it correct for user
   buffers - DMA the contiguous run into a KERNEL bounce buffer (DMA-safe), then
   CPU-copy to 'out'. Per-call bounce from pmm (capped; fall back to the per-block
   slow path on alloc failure) so it stays reentrant. The ELF-load path keeps its
   speed; user reads become correct. After that: claude should read the staged
   33657-byte .claude.json intact and boot into its real UI (no config menu).
   Note: rename rewrite (fry1531) stays - it's correct and needed for atomic writes -
   but was never the cause of THIS corruption.
