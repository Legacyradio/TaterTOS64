KEY NEGATIVE on the EPOLLONESHOT theory:
- The kernel epoll IGNORES EPOLLONESHOT. struct epoll_item has only {fd,events,data,et,et_valid,et_token,next} — no oneshot field; lx_epoll_ctl_fd only sets item->et from EPOLLET (syscall.c:4268,4279). lx_epoll_to_fry drops the ONESHOT bit. So fd 0 is LEVEL-triggered POLLIN and poll_check_fd(fd=0) reports ready whenever the inbuf is non-empty. => fd 0 would be reported ready every epoll pass that has buffered input. Oneshot is not the blocker.

---------------------------------------------------------------------------------
WHAT IS ACTUALLY WEDGING IT (evidence)
---------------------------------------------------------------------------------
The main thread is buried in a SYNCHRONOUS openat storm and isn't returning to epoll_pwait2 often enough / at the right time to consume stdin. Top openat targets this run:
   119  /proc/self/stat        (ENOENT every time -- procfs has no self/stat)
    45  /EFI/FRY, /EFI/BOOT/FRY, /EFI/BOOT, /EFI   (path search churn)
    16  /nvme/.claude.json
    12  /etc/claude-code/managed-settings.d
     7  /proc/version          (ENOENT)
     6  /proc/self/maps        (ENOENT)
   + repeated /usr/lib/python3.14, /usr/lib/.../librt.so.1 (a child being spawned/retried even without MCP)
The tail of the run is almost pure /proc/self/stat (fail) — a hot loop reading a procfs file that does not exist. Whatever component polls /proc/self/stat is spinning on ENOENT and not yielding the main thread back to the interactive read.

So: NOT the OS keyboard path (delivery works), NOT MCP (ruled out), NOT epoll oneshot (not implemented/ignored). The remaining wedge is app-runtime busy-looping on missing procfs (/proc/self/stat, /proc/self/maps, /proc/version) + residual subprocess spawn churn (python/librt), which keeps the main thread off the stdin read.
