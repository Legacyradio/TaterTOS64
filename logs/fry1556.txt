The bug is that Claude's MAIN THREAD (pid=14) stops calling epoll_pwait2 on epfd=5 (the set that contains fd0) after startup (~12 calls), so there is no waiter on stdin when input arrives.

---------------------------------------------------------------------------------
WHAT THE MAIN THREAD DOES INSTEAD (pid=14, after chk=12)
---------------------------------------------------------------------------------
Not blocked — actively busy-looping on:
  nr=45 recvfrom -> rc=-11 EAGAIN (polling a socket for data that isn't there)
  nr=4  stat     -> rc=-2 ENOENT
  nr=89 readlink, nr=262 newfstatat, nr=83 mkdir, nr=257 openat
  nr=233 epoll_ctl -> rc=-17 EEXIST (re-adding an already-present fd)
  nr=202 futex -> WAKE calls (rc=1, waking workers) -- i.e. it is the producer, not parked
Plus /proc/self/stat read ~114x (periodic ~100ms monitor; benign now that it succeeds).

The recvfrom(EAGAIN) spin is the tell: the main thread is polling a socket waiting for a NETWORK RESPONSE and is NOT returning to the interactive epoll(stdin) loop. So Claude is most likely stuck waiting on an in-flight network/API operation to complete (or an init step that depends on it) and never reaches the "idle, epoll stdin for the prompt" state. That is why the UI renders but input is dead.
