fry1556 (FAILED): same image EXCEPT this build (fry1559) ADDED the TBEPW beacon (fry1558) on top of TBFD0.

writes are slow; firing them on pid=22's 75 epfd=14 polls + every epoll pass adds latency that CHANGES SCHEDULING
timing. Strong possibility this is a HEISENBUG: the diagnostic serial I/O slowed the busy network/worker threads
enough that the main thread (pid=14) now gets CPU to poll epfd=5 while a keystroke is buffered -> reads it.

=> Two possibilities, must distinguish before claiming a real fix:
   (1) It genuinely works now (cumulative: panic fix + /proc/self/stat + the loop just needed the timing) and earlier
       failures were the user typing outside the brief epfd=5 poll window; or
   (2) HEISENBUG: the debug beacons' serial latency is what makes it work, and removing them brings the bug back.
If (2), the real fix is to deliberately yield/slow the right thread or fix the scheduling so the main thread reliably
reaches epfd=5 — i.e. a real scheduler/event-loop-fairness fix, NOT relying on debug spew. The recurring signal all
along (main thread starved out of epfd=5 by busy network/worker threads) points at THREAD FAIRNESS / starvation.
