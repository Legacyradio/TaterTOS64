---------------------------------------------------------------------------------
ROOT CAUSE
---------------------------------------------------------------------------------
The main JS thread (Bun on JavaScriptCore) parks in an INFINITE JSC ParkingLot futex wait and never gets woken. With
the event loop thread suspended, nothing polls epfd=5 (the stdin set) anymore, so keystrokes delivered after the park
sit unread in the inbuf (delivery still works; the consumer is asleep). This is a LOST WAKEUP / deadlock in the kernel
futex layer, specifically the JSC futex path (the TBFUTEX jsc-wait / jsc-wake handlers), surfacing under Bun's
multi-thread coordination. It is intermittent/timing-dependent: the fry1558/1554 debug beacons' serial latency shifted
scheduling enough to open a working WINDOW before the park (which is why "hhello" got through this run).

Why it is the OS, not Claude: Bun/JSC runs fine on real Linux; the difference is TaterTOS's custom futex implementation.
A jsc-wake that fails to wake a parked jsc-wait (race between the wait registering and the wake scanning the queue, or
a hashing/validation mismatch between the jsc-wait and jsc-wake paths) leaves the main thread asleep forever.

NOT the cause (all ruled out earlier): OS input delivery (works), kernel epoll/poll_check_fd (accurate), MCP, missing
/proc/self/stat, DNS/network (works), spurious socket readiness. The freeze is purely the main thread never resuming.
