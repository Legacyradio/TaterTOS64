INTERPRETATION
---------------------------------------------------------------------------------
JSC garbage collection on Linux suspends all mutator threads via a signal (here sig=30) so the collector can scan
their stacks/registers at a safepoint, then resumes them. The handler is supposed to PARK the thread (wait on a
semaphore/condition) until the GC says resume. In TaterTOS the threads run the handler and RETURN immediately
(sigreturn) instead of staying parked -> the GC coordinator (pid=15) never gets all threads stopped -> the
stop-the-world barrier never completes -> the GC-initiating MAIN thread (pid=14) busy-waits in userspace for "world
stopped" and never returns to the event loop -> stdin stops being polled -> input freezes (after working in the
pre-GC window: "hhello" got through).

Likely OS-side causes (to confirm): (a) the sig=30 handler's park primitive (a futex/semaphore/sigsuspend) doesn't
actually block in TaterTOS, so the thread resumes immediately; and/or (b) 16 sig=30 are not delivered to threads
blocked in syscalls (futex/epoll) -> those threads never reach the safepoint. Either breaks stop-the-world.
