===================================================================================
ROOT CAUSE (mechanism, fry1563-1564)
===================================================================================
The freeze is JSC's stop-the-world garbage collector failing to suspend threads:
- pid=15 = JSC GC/coordinator. To GC, it suspends every other tgid=14 thread via signal sig=30 (handler 0x4c23470),
  scans their stacks, then resumes them. The main thread (pid=14) initiates GC and busy-waits (userspace) for the
  world to stop before continuing its event loop.
- The sig=30 handler parks the thread with rt_sigsuspend (nr=130) until resume. TaterTOS rt_sigsuspend
  (syscall.c:1662) DOES block: `while(!lx_pending_handled_mask(cur)){sched_block;sched_yield;}`.
- BUG OBSERVED: rt_sigsuspend returns -EINTR (rc=0xfffffffffffffffc) IMMEDIATELY. Reason: while the thread runs its
  sig=30 handler, pid=15 queues ANOTHER sig=30 to it (seen in-trace: "TBSIG queue sender=15 target=19 sig=30" between
  deliver and sigreturn). JSC's sigsuspend mask UNBLOCKS sig=30 (to receive resume), so the already-pending duplicate
  sig=30 makes sigsuspend return at once -> handler returns (sigreturn) -> thread RESUMES instead of staying parked.
- WHY pid=15 sends duplicates: it never receives the handler's "I am suspended" confirmation (a semaphore = futex
  post from the handler back to the coordinator), so it retries the suspend signal. sig=30 lifecycle counts:
  queue=122, deliver=106, sigreturn=106 -> 16 suspend signals queued-but-never-delivered; pid=15 keeps re-signaling
  19/41 AFTER the freeze.
NET: stop-the-world never completes -> pid=14 (main/event loop) hangs waiting -> stdin no longer polled -> input dead.
It is intermittent because the debug beacons' serial latency opened a brief pre-GC window where typing worked.
