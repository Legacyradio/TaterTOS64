THE "FREEZE" ROOT CAUSE — RESOLVED (NOT a deadlock)
---------------------------------------------------------------------------------
TBDPF (demand-page beacon) is decisive: pid=14's fault cr2 ADVANCES one page each fault —
  cr2 ...9241000 -> 9242000 -> 9243000 -> 9244000 ...   (rip in a tight zero/touch loop)
then jumps to new regions (6FBBFEC76000, 6FC020664000 ...), n climbing 0x1000/0x2000/0x3000/0x4000+.
=> the main thread was DEMAND-PAGING large userspace regions (Bun/JSC heap/gigacage/response buffers) 4KB at a
time via #PF. cr2 ADVANCING (never fixed) = it PROGRESSES; it is not a hang. The earlier "freezes" were this slow
page-in (page-fault-bound), which LOOKS frozen — and the diagnostic beacons' timing/our patience occasionally let
it finish (the intermittency). 6 deadlock theories were disproven because there was no deadlock to find.

FIX (performance, keeps Claude fully networked):
- Batch/pre-fault: on a USER #PF in a known anon/JSC region, commit a RUN of pages (e.g. 16-64) per fault instead of
  one, or pre-populate large mmaps; consider 2MB huge pages for the big regions. Cuts fault count ~16-64x -> the
  apparent freeze becomes a brief pause. lx_try_demand_page (irqdesc.c:531) + the mmap commit path are the sites.
- This is the ONLY remaining item for smooth interactivity. It already FUNCTIONS; it is just slow on big allocations.
