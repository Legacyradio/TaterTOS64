ROOT CAUSE: ceval.c hardware_stack_limits() uses pthread_getattr_np(pthread_self)
  + pthread_attr_getstack to get the C-stack top (HAVE_PTHREAD_GETATTR_NP=1 in
  pyconfig_tater.h; the Emscripten workaround is __EMSCRIPTEN__-gated, inactive).
  TaterTOS pthread_getattr_np (pthread.c) returns SUCCESS with
  attr->_stackaddr/_stacksize = pi->thr.stack_base/stack_len. For the main
  thread (lazily registered in fry1677 with a zeroed fry_thread) both are 0 ->
  CPython top = stack_addr+stack_size = 0 -> assert(top!=0) aborts. This is a
  direct consequence of fry1677 (before it, pthread_self()=0 -> find_pth fails
  -> ESRCH -> CPython already used its fallback; now the main thread resolves to
  a real-but-stackless slot).

FIX: src/user/libc/pthread.c pthread_getattr_np() — if the resolved thread has
  no recorded stack (stack_base==0 || stack_len==0), return EINVAL instead of
  success. CPython's hardware_stack_limits() then falls through to its
  stack-pointer-based estimate (top=round_up(sp+..), base=top-Py_C_STACK_SIZE),
  which is valid (non-zero) for the main thread. Real pthread_create threads are
  unaffected (they have stack_base/len set).
