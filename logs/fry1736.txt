WHY THE linux_like APPROACH WAS WRONG (Zack caught it; I should have known from planv3):
  - TaterTOS is a 100% INDEPENDENT x86-64 UEFI-native OS: its own kernel, ABI, FS,
    scheduler, driver base, native userspace, system identity. It offers POSIX SOURCE
    compatibility + an OPTIONAL Linux binary personality (the subsystem) — but Linux
    is NOT the native path. Treating tatertos as "linux_like" / linux-ABI-equal was a
    category error.
  - PROOF the ABI is genuinely distinct (src/include/tatertos/syscall.h, single source
    of truth): SYS_WRITE=0, SYS_READ=1, SYS_EXIT=2, SYS_OPEN=5, SYS_MMAP=52, SYS_GETTID
    =67, SYS_GETRANDOM=85, SYS_CLOCK_GETTIME=86, SYS_FSTAT=91 ... Linux x86-64 is
    write=1/read=0/exit=60/open=2/mmap=9/getrandom=318. NONE match. linux_like would
    have bound Rust std to WRONG syscall numbers -> immediate catastrophic breakage.
