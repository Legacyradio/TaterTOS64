CHURN DIAGNOSIS (the slow boot):
  - Serial showed "VM COMMIT OK" (syscall.c:2861, printed for the FIRST page of
    each mmap commit) flooding for VA 0x1000003a1000, pages=33, with a NEW
    physical page set each time.
  - Quantified from /tmp/fry1762_serial.log:
      * 2927 total VM COMMIT OK lines this boot.
      * 1402 of them (~48%) are the SAME VA 0x1000003a1000 (a 132 KB / 33-page
        anon-private region), each a fresh distinct PA (hundreds of PAs, not a
        2-page flap).
      * ZERO release/unmap/DONTNEED lines logged.
  - Interpretation: NOT pager eviction/thrashing. It is userspace mmap/munmap
    CHURN — CPython (pid 10) maps a 132 KB region, uses a few pages, munmaps,
    immediately remaps at the same VA (the VA allocator hands back the lowest
    free address), 1400+ times during `import hermes_cli.main` (consistent with
    a zipimport/marshal read window per stdlib .pyc).
  - Why expensive: vm_commit_private_pages (syscall.c:2836) EAGERLY allocs+zeros
    ALL 33 pages on every map, even though most are never touched before munmap.
    1402 x (33 alloc + 33 zero) ~= 46k needless page ops at import time = the
    crawl Zack watched (clock advancing, just slowly).

ROOT CAUSE (pinned): LNX_mmap (syscall.c:5761-5794) only routes anon-private maps
to the LAZY/demand path when `sparse_reserve` is true, which requires
`map_len >= 64 MiB` (NORESERVE) or `>= 4 GiB` (gigacage). A 132 KB map fails the
gate -> falls to the eager path (5796) -> full alloc+zero every cycle.
