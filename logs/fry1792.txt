    4034f6  mov  $0x47,%eax        ; SYS_GET_TLS_BASE (71)
    403505  syscall
    403507  test %rax,%rax

    40350c  mov  %ebx,%edi         ; edi = key
    40350e  mov  0x8(%rax,%rdi,8),%rax   <-- FAULTS
  This is fry_tls_block_ensure()/fry_tls_block_current() INLINED into
  fry_tls_get() (src/user/libc/libc.c:1030 -> :396 -> :495): it treats the %fs
  base as a `struct fry_tls_block *` and reads block->slots[key] at
  base + 8 + key*8.

ROOT CAUSE (arithmetic, confirmed): rax=8, rdi=key=2 -> 8 + 8 + 2*8 = 0x20 = CR2.
Exactly matches. So **SYS_GET_TLS_BASE returned 8**, i.e. cur->user_fs_base == 8
for pid 9's MAIN thread. 8 is neither a valid variant-II TCB (the ELF loader puts
it at 0x7FFF8000_xxxx, see elf.c:431 `*tls_base_out = tp`) nor NULL — so it slips
past the `test/je` NULL guard and derefs low memory.
  rcx=0x403507 == the syscall return address, confirming rax is genuinely the
  syscall's return value and not a clobber.

STATIC AUDIT DONE THIS STEP (no code changed):
  - syscall.c:8544 SYS_GET_TLS_BASE just returns cur->user_fs_base (0 if kernel).
  - process.c:925 / :992 — BOTH process_launch and process_launch_args set
    p->user_fs_base = tls_base from elf_load_fry BEFORE
    process_tls_stash_template(); the fry1790 stash does NOT touch user_fs_base
    (it only writes shared->tls_tmpl + tls_thread_next). So the fry1790 change
    does not obviously corrupt the MAIN thread's base.
  - elf.c:181 defaults *tls_base_out = 0 and only overwrites with tp on a valid
    PT_TLS; a failed/absent PT_TLS gives 0, which would take the SAFE je branch.
    => 8 cannot come from the loader; something SETS it to 8 after start.
  - Candidate setters of user_fs_base after launch: SYS_SET_TLS_BASE
    (syscall.c:8541, from libc fry_tls_set_base) and arch_prctl ARCH_SET_FS
    (syscall.c:6072). The lx_execve path (syscall.c:5475/5527) zeroes it, but

    (syscall.c:8376); with argc=2 it came through the args path. Which exact
    launch path the Shell used for `hermes` is NOT yet pinned down.
  - PRE-EXISTING DESIGN COLLISION (worth flagging): libc's fry_tls_block scheme
    wants %fs to point at a malloc'd `struct fry_tls_block`, while the fry1701-
    1706 ELF-TLS work points %fs at the variant-II TCB. They coexist only because
    the TCB has FRY_TLS_TCB_RESERVE (0x1000) of slack above tp that libc uses for
    slots[] (elf.c:429 documents this). Any code path that calls
    fry_tls_set_base() with a heap block, or that leaves a stale/garbage base,
    breaks one of the two.
