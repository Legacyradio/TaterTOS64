fry1799 — TLS probe redesigned (per-class budgets) + rebuilt/restaged — 2026-08-10
==========================================================================
WHAT: Fixed the fry1798 instrumentation failure so the probe can actually answer
its question. Diagnostic-only changes; NO KERNEL LOGIC WAS ALTERED.

WHY (the fry1798 defect, in one line): one global budget, shared between a HOT
probe (SYS_GET_TLS_BASE on the main thread) and RARE decisive probes
(build/spawn/set). The hot one burned all 96 lines by serial line 171 of 981;
the spawn/abort events at line ~975 printed nothing. Rare events must not
compete with hot events for the same counter.

CHANGES:
  src/kernel/proc/process.c:398-399 — replaced the single counter with two:
      int g_tlsdbg_spawn_budget = 64;   /* build/spawn/set: rare */
      int g_tlsdbg_get_budget   = 64;   /* get: hot, and now gated */
    All four process.c probe sites (build early-out, build OK, spawn NATIVE,
    spawn LINUX_CLONE) now draw from g_tlsdbg_spawn_budget, so they can no
    longer be starved by syscall traffic.

  src/kernel/proc/syscall.c SYS_GET_TLS_BASE — the important change:
    - main thread (cur->pid == cur->tgid): printed EXACTLY ONCE as a baseline
      via a static flag, then silent forever. This is what ate fry1798.
        "TLSDBG get MAIN tid=%u tgid=%u fs=%lx (baseline, printed once)"
    - spawned threads (cur->pid != cur->tgid): logged against the dedicated
      get budget. THIS IS THE DATA THE WHOLE STEP EXISTS FOR — tid=10 is a
      spawned thread (tgid=9), so it now cannot be missed.
        "TLSDBG get THREAD tid=%u tgid=%u fs=%lx"
    Gating on pid!=tgid is exact, not heuristic: the aborting context is
    literally reported as "pid=9 tid=10" by the fault handler.

  src/kernel/proc/syscall.c SYS_SET_TLS_BASE — moved to spawn budget, added
    tgid to the line so an overwrite can be attributed to a specific thread.
