fry1800 — ROOT CAUSE FOUND: libc thread trampoline DESTROYS the kernel's ELF TLS — 2026-08-10
==========================================================================
WHAT: Ran the fry1799 instrumented kernel. The probe answered the question
conclusively. The bug is in USERSPACE libc, not the kernel. fry1790's per-thread
ELF TLS works correctly and has worked since it was written; libc throws it away
microseconds after the thread starts. No source changed this step (diagnosis only).

=== THE DECISIVE SERIAL EVIDENCE (logs/fry1800_serial.log) ===

READ IT IN ORDER:
 1. The kernel BUILT a correct private TLS block for tid=10 at 0x7FFF80100138 —
    bbase 0x7FFF80100000, alloc=312 (0x138 = PT_TLS memsz exactly), in the thread
    arena, and GENUINELY DISTINCT from the main thread's 0x7FFF80000138.
    => fry1790 IS CORRECT. It was never the bug.
 2. path=NATIVE confirms hermes/python3 uses the native thread path
    (SYS_THREAD_CREATE -> process_create_user_thread), NOT the Linux clone path.
 3. Then userspace called SYS_SET_TLS_BASE and REPLACED %fs with 0x10005592C30 —
    a HEAP address (shared->heap_start = 0x10000000000, process.c:67).
 4. Every subsequent get on tid=10 returns the heap value. The thread runs its
    entire life on the wrong TLS base and then aborts.

=== ROOT CAUSE (userspace, exact) ===
src/user/libc/libc.c:935 fry_thread_create()
    tls_block = (struct fry_tls_block *)calloc(1, sizeof(*tls_block));
    ...
    ctx->tls_base = tls_block;            /* heap pointer handed to the thread */

src/user/libc/libc.c:418 fry_thread_trampoline()   <- EVERY native thread starts here
    if (fry_tls_set_base(ctx.tls_base) < 0)        /* libc.c:421 — THE DEFECT */
        fry_thread_exit(1);

The trampoline UNCONDITIONALLY replaces the kernel-provided %fs with a calloc'd
`struct fry_tls_block` (libc.c:376-386: {void *tls_base; void *slots[]; tid;
stack_base; stack_len;}).

WHY THAT KILLS CPython: `struct fry_tls_block` is a BARE STRUCT ON THE HEAP. It
has NO ELF TLS IMAGE BENEATH IT. x86-64 variant II puts __thread variables at
NEGATIVE offsets from tp. python3.elf's PT_TLS is FileSiz 0x79 / MemSiz 0x138 /
align 8, and the symbols are:
    _mi_heap_default   TLS offset 0x00   (.tdata)
    _Py_tss_tstate     TLS offset 0x88   (.tbss — past FileSiz, so ZERO in a
                                          properly built block)
With tp = heap block, _Py_tss_tstate resolves to (heap_block - 0x138 + 0x88) =
heap_block - 0xB0 — i.e. WHATEVER HEAP BYTES PRECEDE THE ALLOCATION. Non-zero
garbage => _PyThreadState_Attach sees a non-NULL "old thread state" => Fatal
Python error. Identical reasoning applies to mimalloc's _mi_heap_default at
offset 0 (tp - 0x138).
This is TWO TLS MECHANISMS FIGHTING OVER %fs: TaterTOS's legacy key-slot TLS
(heap `fry_tls_block`, predates ELF TLS) vs the kernel PT_TLS support added in
fry1790. The main thread never breaks because nothing overwrites what elf.c set.

=== THE DESIGN ALREADY ANTICIPATED THIS (so the fix is the intended shape) ===
  src/kernel/proc/elf.c:66
      #define FRY_TLS_TCB_RESERVE 0x1000ULL  /* room for libc struct fry_tls_block */
  src/kernel/proc/process.c:377
      #define FRY_TLS_TCB_RESERVE_P 0x1000ULL
  process.c:417  map_end = (tp + FRY_TLS_TCB_RESERVE_P + 0xFFF) & ~0xFFF
  process.c:425  *(uint64_t *)tp = tp;   /* variant-II self-pointer */
  libc.c:377-381 comment: "tls_base MUST be the first member: it sits at offset
      0 == %fs:0, the x86-64 variant-II TLS self-pointer".
The reserve above tp EXISTS to hold libc's fry_tls_block, and the kernel ALREADY
writes the self-pointer that is that struct's first member. The main thread uses
exactly this arrangement. Only the spawned-thread path fails to.

=== NEXT (fry1801, PROPOSED — NOT approved, awaiting Zack) ===
Make spawned threads use the kernel's block instead of a heap one, matching the
main thread:
  1. libc.c fry_thread_trampoline(): DELETE the fry_tls_set_base() call. The
     kernel has already set a correct %fs before the thread's first instruction
     (process_start -> write_user_fs_base, process.c:162).
  2. libc.c fry_thread_create(): stop calloc'ing tls_block. stack_base/stack_len
     must still reach pthread_getattr_np (pthread.c:184) — carry them in the
     bootstrap ctx and have the trampoline write them into the block AT tp
     (inside FRY_TLS_TCB_RESERVE), where the kernel already wrote tls_base=tp.
  3. Keep a guarded fallback: if the kernel gave %fs == 0 (a binary with no
     PT_TLS), retain the legacy heap path so non-ELF-TLS apps keep working.

requires RELINKING python3.fry (`make -f Python3.mk python3`), not just `make
kernel`. Then rebuild/restage the ISO.
