=== THE CHANGE (src/user/libc/libc.c, fry_thread_trampoline) ===
BEFORE (libc.c:421) — every native spawned thread unconditionally replaced %fs:
    if (fry_tls_set_base(ctx.tls_base) < 0) { fry_thread_exit(1); }
AFTER:
    if (!fry_tls_get_base()) {
        if (fry_tls_set_base(ctx.tls_base) < 0) { fry_thread_exit(1); }
    } else {
        block = (struct fry_tls_block *)fry_tls_get_base();
    }

WHY (fry1800 evidence): the kernel (fry1790) builds a correct per-thread
variant-II PT_TLS block and sets %fs BEFORE the thread's first instruction
(process_start -> write_user_fs_base, process.c:162). The trampoline then threw
it away and pointed %fs at a calloc'd `struct fry_tls_block`, which has NO ELF
TLS image beneath it. x86-64 variant II resolves __thread vars at NEGATIVE
offsets from tp, so CPython's _Py_tss_tstate (TLS offset 0x88 -> tp-0xB0) and
mimalloc's _mi_heap_default (offset 0x00 -> tp-0x138) landed on unrelated heap
bytes. Non-zero garbage in _Py_tss_tstate is exactly
"_PyThreadState_Attach: non-NULL old thread state".
Serial proof from fry1800:
    build tid=10 OK fs=7fff80100138      (kernel builds it correctly)
    spawn path=NATIVE tid=10 parent=9    (native path, not linux clone)
    set   tid=10 old_fs=7fff80100138 new_fs=10005592c30   <- the defect
    get   THREAD tid=10 fs=10005592c30   (x20, then abort)

WHY THIS SHAPE (scope was deliberately cut down): an earlier draft also removed
the calloc and relocated stack_base/stack_len into the TCB. Zack pushed back that
that was unnecessary — correct. The calloc stays; for a PT_TLS binary the heap
block is simply unused. The `else` branch repoints `block` at the kernel's block
so the following code still populates tls_base/thread_tid in the RIGHT place
(the TCB reserve at tp), which pthread_self() depends on.

WHY IT IS SAFE FOR EVERYTHING ELSE:
 - Binaries with NO PT_TLS get fry_tls_get_base()==0 and take the legacy heap
   path completely unchanged. No behavior change for non-ELF-TLS apps.
 - The key-slot TLS API (fry_tls_get/set) keeps working with no edits:
   fry_tls_block_ensure() reads %fs, now gets the kernel's tp, and lands slots[]
   in the TCB reserve — which is precisely what that reserve is FOR:
     elf.c:66  #define FRY_TLS_TCB_RESERVE 0x1000ULL /* room for libc struct
                                                        fry_tls_block */
   The kernel already writes the struct's first member for us (process.c:425
   *(uint64_t*)tp = tp), and libc.c:377-381 documents that tls_base must be
   first because it IS %fs:0. The main thread has always worked this way; only
   spawned threads did not.
 - SIZE CHECKED: sizeof(struct fry_tls_block) = 8 (tls_base) + 8*64 (slots)
   + 4 (+4 pad) (thread_tid) + 8 (stack_base) + 8 (stack_len) = 544 bytes,
   against a 4096-byte reserve. Fits with ~3.5KB headroom. Verified, not assumed.

KNOWN, ACCEPTED CONSEQUENCE: stack_base/stack_len at tp are zero for spawned
threads, so pthread_getattr_np (pthread.c:184) returns EINVAL and CPython falls
back to its stack-pointer-based estimate. That is the SAME deliberate fallback
the main thread already takes — see the fry1678 comment at pthread.c:176-185.
Known-good path, not new risk. If a spawned thread ever needs real stack attrs,
that is a separate step.
