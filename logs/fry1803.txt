=== asyncio: THE MECHANISM AT ISSUE (stated precisely, NOT yet diagnosed) ===
asyncio/__init__.py:8 does `from .base_events import *`, then line 26 references
the BARE NAME `base_events`. In CPython that name resolves only because importing
a submodule binds it as an attribute on the parent package —
_bootstrap._find_and_load_unlocked() does:
      setattr(parent_module, name.rpartition('.')[2], module)
and __init__.py's globals ARE the asyncio module's __dict__. The failure is on
the FIRST submodule in the list, so the suspicion is that parent-attribute
binding, not anything asyncio-specific. Note that path only executes when the
submodule is NOT already in sys.modules; if it is, _handle_fromlist takes over
instead. A partially-initialised asyncio in sys.modules would therefore change
which path runs.
DO NOT act on the above as a conclusion — it is the hypothesis to TEST. fry1789
was wrong from exactly this kind of static reading.
