=== CHANGE 1 — THE ACTUAL FIX (fry1804 root cause) ===
src/include/unistd.h:  + #define _SC_IOV_MAX 60      (the Linux value)
src/user/libc/posix.c sysconf():  + if (name == _SC_IOV_MAX) return 1024;
WHY: asyncio/selector_events.py:33-39 does
    _HAS_SENDMSG = hasattr(socket.socket, 'sendmsg')
    if _HAS_SENDMSG:
        try: SC_IOV_MAX = os.sysconf('SC_IOV_MAX')
        except OSError: _HAS_SENDMSG = False
Upstream guards it, but ONLY against OSError. CPython builds os.sysconf_names
from #ifdef _SC_* guards; with the macro undefined the NAME did not exist and
os.sysconf() raised ValueError("unrecognized configuration name"), which escaped
the handler and aborted the asyncio import. That abort was then MASKED on retry
as the bogus "NameError: name 'base_events' is not defined" (fry1804).
1024 = Linux IOV_MAX. Returning a real value keeps asyncio's sendmsg batching
path enabled rather than silently degrading to send().
REJECTED ALTERNATIVE: patching asyncio/selector_events.py to catch ValueError —
wrong layer (hides an OS gap in the stdlib) and would need re-applying on every
Python upgrade.

=== CHANGE 2 — LATENT Python3.mk BUG, FOUND BY THIS REBUILD ===
SYMPTOM: after wiping objects for the fry1805 rebuild, the link failed:
  x86_64-elf-ld: cannot find .../build-tatertos/Modules/_sqlite/module.o
  (and connection/cursor/statement/row/blob/prepare_protocol/util/microprotocols)
222 of 232 objects built; the 10 _sqlite objects were never compiled.
ROOT CAUSE: CPYTHON_ALL_OBJS (line ~203) referenced $(CPYTHON_SQLITE_OBJS), but
that variable was not defined until line ~330 — AFTER the `python3:` rule that
consumes it. Make expands a rule's PREREQUISITES when the rule is READ, so the
sqlite objects expanded to EMPTY and were never prerequisites. The RECIPE expands
at execution time, when the variable IS set, so the link command still listed
them. Net: make never built them, ld demanded them.
WHY IT WAS INVISIBLE UNTIL NOW: those .o files survived from an older build, so
the missing dependency never mattered. Deleting them exposed it. This is a
dormant landmine for anyone doing a clean build — it would have detonated on the
first `make clean` regardless of this session.
FIX: moved CPYTHON_SQLITE_SRCS / CPYTHON_SQLITE_OBJS definitions ABOVE
CPYTHON_ALL_OBJS, with a comment recording the make semantics so it is not
"tidied" back later.
(Verified in isolation first: building one sqlite object by ABSOLUTE path
succeeded — the pattern rule itself was always fine, only the prerequisite
expansion was broken. Note the objdir is an absolute path, so a relative target
gives a misleading "No rule to make target".)
