CANDIDATE DIRECTIONS FOR fry1811 (hypotheses — NONE tested, do not act as fact):
 1. A LOCK. ~/.hermes contains auth.lock, and hermes uses file locking around
    auth. If the port's fcntl/flock (F_SETLKW) is a stub that never returns —
    or returns "would block" in a retry loop — startup would hang exactly like
    this, before any network use. NOTE: auth.lock was deliberately NOT staged
    this step, so its ABSENCE could equally be the trigger (a lock file the code
    expects to create/acquire). Check libc fcntl/flock behaviour first — it is
    cheap and would explain the symptom precisely.
 2. A thread/futex wait. fry1808/1809 both show only "TLSDBG get MAIN"; no
    spawned-thread lines this run, so if the agent expects a worker thread that
    never starts, the main thread would wait forever. The TLSDBG probes are still
    compiled in and would show a spawn if it happened — they show none.
 3. A blocking read on stdin despite -z. isatty() returns TRUE for fd 0-2
    (posix.c:574), so any code path that probes "am I interactive?" gets yes and
    may wait for input even in one-shot mode. Making isatty() honest per-fd is a
    real option but changes behaviour OS-wide — do not do it casually.
