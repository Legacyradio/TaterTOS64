=== ROOT PROBLEM FOUND: DEAD INSTRUMENTATION FROM A CLOSED INVESTIGATION ===
TBSPIN/TBCLK/TBMAIN/TBPROCIN are leftovers from the fry1571-1577 Claude spin
hunt. lapic_timer.c:47 literally says "REMOVE once fixed". They were never
removed. TBSPIN is emitted from inside the LAPIC TIMER INTERRUPT HANDLER via
early_serial_puts(), which writes the serial port ONE BYTE AT A TIME with port
I/O. That is per-tick overhead on every CPU, forever, plus it buries real program
output — which is exactly why hermes' behaviour has been so hard to read all
session, and plausibly a real contributor to the "demand-paging crawl".

=== FIX + A BUG I INTRODUCED AND THEN FIXED (recorded honestly) ===
STEP 1: syscall.c:157 `g_tb_trace_claude_tgid` 3u -> 0u.
  It was hardcoded to 3, so it traced pid 3 (TaterBridge main) from boot forever.
  tb_trace_is_claude() still sets it when a process named RCLAUDE/claude starts,
  so Claude tooling keeps tracing on demand. RESULT: TBSPIN 599,643 -> 0. GOOD.
STEP 2 — MY CHANGE MADE TBMAIN WORSE, NOT BETTER:
  Measured after step 1: TBSPIN 0, but TBMAIN 42,804 in ONE boot (43,018 lines
  total). CAUSE: sched.c's census filter is
      if (procs[i].tgid != TB_TRACE_CLAUDE_TGID &&
          procs[i].pid  != TB_TRACE_CLAUDE_TGID) continue;
  With the traced tgid set to 0 this INVERTS: it stops skipping, and instead
  MATCHES every UNUSED proc-table slot (pid 0 / tgid 0). Setting the tracer to
  "off" switched a different diagnostic ON. I caused this; I measured it; I fixed
  it rather than shipping it.
STEP 3: gated the whole heartbeat block on the tracer being enabled:
      if (TB_TRACE_CLAUDE_TGID && (g_tbclk_ticks[cpu] % 5000ULL) == 0) {
  (sched.c, with a comment explaining the inversion so it is not "tidied" back.)

RESULT — MEASURED, SAME POINT IN BOOT:
  BEFORE: 43,018 serial lines   TBSPIN 0 (after step 1) / TBMAIN 42,804
  AFTER:  **40 serial lines**   TBSPIN 0  TBCLK 0  TBMAIN 0  TBPROCIN 0
