=== FINDING 2 — state.db IS 0 BYTES (the sharpest lead) ===
/.hermes/ listing: state.db  size = 0.
hermes_state.SessionDB opens SQLite at this path and initialises a schema. A
0-byte file = the file was created by sqlite3.connect() and the database header
was NEVER written, across every run since 2026-08-11.
hermes_state.py:39-56 (verified in the STAGED copy) documents exactly the risk:
    "SQLite's WAL mode requires shared-memory (mmap) coordination and fcntl
     locking ... On those filesystems PRAGMA journal_mode=WAL raises
     OperationalError('locking protocol') ... fall back to journal_mode=DELETE"
The fallback is triggered by MATCHING EXCEPTION TEXT (_WAL_INCOMPAT_MARKERS).
HYPOTHESIS, NOT YET TESTED: if TaterTOS's mmap/fcntl BLOCKS rather than raising,
no marker is ever matched, the fallback never runs, and startup waits forever —
with state.db left at 0 bytes, which is what the image shows.
This is consistent with fry1810's untested candidate #1 (a lock), arrived at
independently from a different artifact.

=== FINDING 5 — TIMESTAMPS ARE MISSING FROM EVERY LOG LINE ===
Every line in both log files begins with a bare milliseconds field, e.g.
    ",248 WARNING hermes_cli.plugins: ..."
logging's default asctime is strftime(datefmt, ...) + ",%03d" % msecs. The
",%03d" tail is present and correct; the ENTIRE strftime portion is empty.
=> strftime() (or its localtime input) returns an empty string in this port.
UNTESTED, and flagged because it is the right SHAPE for a hang: if time
functions are unreliable, any deadline/backoff/timeout computation built on them
can wait effectively forever. Do NOT treat this as the cause — it is a lead to
probe, nothing more.
