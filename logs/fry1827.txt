=== WHAT I GOT WRONG ===
fry1825 stated "SHELL_EXIT=0 ... compiled with no diagnostics". That was false.
The command was:
    make shell.tot
`shell.tot` is NOT a make target. The Makefile's target is `shell`
(.PHONY line 229; the rule produces shell.tot as a by-product). So make matched
nothing, did no work, and exited 0. I read that 0 as "compiled clean".
THE TELL I HAD AND DID NOT USE: shell.tot's mtime stayed at 21:12 — the
PREVIOUS build. I checked mtimes religiously for the libc work in fry1819 and
then did not check here. An artifact that did not change mtime did not get
rebuilt, and an EXIT=0 from a build that did nothing is not a pass.
This is [[feedback_verify_before_claiming_success]] and it is the same failure
class as the stubs this whole session has been about: something returned
success without doing the work, and I believed it.

=== THE REAL BUILD, AND THE REAL ERROR ===
  make          (default target, which actually builds the shell)
    src/user/shell/shell.c:885:18: error: 'FRY_PATH_MAX' undeclared
    src/user/shell/shell.c:1148:19: error: 'FRY_PATH_MAX' undeclared
    make: *** [Makefile:304: src/user/shell/shell.o] Error 1
    MAKE_EXIT=2
CAUSE: shell.c includes libc.h, fry.h, gfx.h, taterwin.h, unistd.h, fcntl.h,
sys/stat.h, sys/socket.h, netinet/in.h, arpa/inet.h, signal.h, stdio.h — and
reaches fry_limits.h through NONE of them, directly or transitively. The
fry1824 resolve_program() and the rewritten fallback both declare
char buf[FRY_PATH_MAX].
It compiled in process.c (fry1822/1823) because process.h pulls fry_limits.h
in; I carried that assumption across to a different file without checking.

=== FIX ===
src/user/shell/shell.c — added #include <fry_limits.h> with a comment saying
why. One line, no logic change.
