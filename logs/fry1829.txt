=== ❌ THE CLICK MISSED — CAUSE IDENTIFIED ===
Ran the fry1811 recipe: query geometry, windowactivate --sync, mousemove to
absolute coords, click 1.
  window geometry at query time: 1280x800+2556+276
  computed target: (2556+1223, 276+347) = (3779, 623)
  expected guest coords: (1223, 347) = the Shell dock icon
  SCREENSHOT SHOWS: pointer rendered at roughly (640, 406) in the guest, and
  no Shell window. Nothing was clicked.
CAUSE: the QEMU command line has no pointer device, so the guest gets the
default PS/2 mouse, which is RELATIVE. Absolute host coordinates cannot map
onto a relative pointer — xdotool moves the host cursor to (3779,623) and QEMU
delivers a movement DELTA to the guest, which lands wherever the guest's own
pointer happened to be plus that delta. The arithmetic in the recipe assumes an
absolute device that was never present.
This also means the fry1811 recipe is not reliable as written. It appears to
have worked there by luck of the accumulated delta, which is why the same recipe
produced a hit once and a miss now.

=== FIX APPLIED (launch flags only, no rebuild) ===
Relaunched with:  -usb -device usb-tablet
A USB tablet is an ABSOLUTE pointing device: the guest receives the actual
coordinate, so host-to-guest mapping becomes exact and repeatable. This is the
standard fix and costs nothing but two flags. Continues in fry1830.

=== NOTE FOR THE RECIPE ===
fry1811's xdotool recipe should be amended wherever it is referenced: it is
correct ONLY when the VM was launched with an absolute pointer. Without
-device usb-tablet the coordinate maths is meaningless. launch_debug.sh does
not include it either, nor -smp.
