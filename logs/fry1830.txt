=== WHY THE TABLET WAS NEVER GOING TO HELP (the part fry1829 missed) ===
TaterTOS has PS/2 input drivers — src/drivers/input/ps2_ctrl.c and ps2_kbd.c.
There is no USB HID driver in the tree. A usb-tablet is therefore an emulated
device that NOTHING IN THE GUEST IS LISTENING TO. Adding it changed the QEMU
command line and nothing else. I proposed a host-side fix for what is a
guest-side driver question, and did not check whether the guest could consume
the device before recommending it. That is the same mistake pattern as reading
an exit code without checking an mtime (fry1827).

=== WHY PHYSICAL CLICKS WORK BUT SYNTHETIC ONES DO NOT ===
Zack clicked the dock icon successfully on the fry1821 boot ("i clicked it
smarty pant"), so mouse input from a REAL device reaches the guest fine.
The difference is how QEMU sources motion in relative mode: it consumes events
from the physical pointing device. A pointer warp — which is what xdotool
mousemove and mousemove_relative both perform — does not present as physical
device motion, so QEMU has nothing to forward.
KEYBOARD IS UNAFFECTED: xdotool key/type via XTEST after windowactivate --sync
is proven working on this project (fry1808 typed whole commands that way,
fry1811 re-confirmed). Only the MOUSE path is dead.

The click-to-grab attempt caused QEMU to grab the host pointer. Verified it was

would have hijacked his mouse with no explanation. Any future attempt at mouse
injection must verify the grab state afterwards and release it.
